<Callout type="warn">

Experimental. `remote run` runs tasks of a published build file from a git ref of the
repository. Sending a run of the files on your machine (`--on`, running a task with a
`runner:`) arrives in follow-up releases, see
the [remote compute spec](https://github.com/no0dles/hammerkit/blob/master/specs/remote-compute/spec.md).

</Callout>

`remote` manages the list of hammerkit servers your machine knows about. Each one
is registered under a short name, which later features (`--on <name>`, a task's
`runner:`) refer to instead of a URL.

How a server is set up, and how it decides who may run what, is described in
[Remote compute](/docs/remote-compute).

```bash
hammerkit remote add build https://build.example.com --issuer https://login.example.com
hammerkit remote login build
hammerkit remote accounts build
hammerkit remote publish build
hammerkit remote run test --server build
hammerkit remote approvals build
hammerkit remote approve run_Qx3k9ZpL2mW7vN4a build
hammerkit remote list
hammerkit remote use build
hammerkit remote remove build
```

Except for `publish` and `run`, the commands only touch your host config and talk to the
server, so they work with or without a build file in the working directory.

## Commands

| Command | What it does |
| --- | --- |
| `remote add <name> <url> --issuer <url>` | Register a server. `--issuer` is the OAuth issuer the server accepts tokens from, written exactly as the `iss` of its tokens (some providers end it with a slash). `--client-id`, `--audience` and `--scope` pin what a login asks for, see [Signing in](#signing-in). |
| `remote list` | Show the registered servers and which one is the default. |
| `remote use <location>` | Set the default location: `local`, `auto` or a registered name. |
| `remote remove <name>` | Forget a server. If it was the default, runs are local again. |
| `remote login <name>` | Sign in to the server with your identity provider. |
| `remote logout <name>` | Forget the sign-in. |
| `remote accounts [name]` | Show who you are on the server and which service accounts you may use. Without a name, the default server. |
| `remote publish [server]` | Publish the build file of the working directory (or the one `--file` names) and the files it includes, and print its hash, see [Publishing](#publishing-a-build-file). |
| `remote run <tasks...>` | Run tasks of a published build file on a server from a git ref, print their output and exit as they did, see [Running tasks](#running-tasks). |
| `remote versions [server]` | List the published versions, newest first, with who published them, where they come from and whether they were yanked. `--filter key=value` (repeatable) keeps the ones with that [annotation](/docs/remote-compute/build-files#annotations). |
| `remote approvals [server]` | List the runs that wait for your approval. |
| `remote show <run or hash> [server]` | Show a run that waits for your approval, or a proposed or published version, in full: per task the commands, image, secrets and accounts, and every file of a version, see [Approving runs](#approving-runs) and [Proposing](#proposing-a-version). |
| `remote proposals [server]` | List the proposed versions of build files you made or may approve, see [Proposing](#proposing-a-version). |
| `remote approve <run or hash> [server]` | Let a run go ahead, or publish a proposed version. `--reason <text>` is optional. |
| `remote yank <hash> [server]` | Pull a published version back: no run starts from it. `--reason <text>` is shown to whoever tries to run it. Needs `builds: publish` or `use` of an account the version works with. |
| `remote unyank <hash> [server]` | Let a yanked version go on. Needs `builds: publish`. |
| `remote reject <run or hash> [server]` | End a run, or drop a proposed version. `--reason <text>` is shown to who asked for it. |
| `remote mcp` | Serve a sandbox on a server as MCP tools over stdio for a coding agent, see [remote mcp](/docs/cli/remote-mcp). |

Re-running `remote add` with the same values changes nothing. To point an existing
name at a different server pass `--force`, so a typo can't silently redirect your
runs.

`local` and `auto` are reserved and can't be used as server names.

## Host config

Registrations live in `~/.hammerkit/config.yaml`. Set `HAMMERKIT_CONFIG` to use a
different file.

```yaml
servers:
  build:
    url: https://build.example.com
    issuer: https://login.example.com
run:
  on: build
```

<Callout type="info">

The config is deliberately not part of the project's build file. A checked-in file
naming a server URL could redirect your source code and OAuth tokens, so the
decision of where to send work stays on the machine.

</Callout>

## URLs

Server URLs must use `https`. Plain `http` is accepted only for `localhost`,
`127.0.0.1` and `[::1]`, for local testing. URLs with credentials, a query string
or a fragment are rejected, and a trailing slash is dropped.

## Publishing a build file

A server runs published build files, it does not take task definitions from the one
who runs them. `remote publish` sends yours:

```
$ hammerkit remote publish build
published to build: sha256:9f2c61d0... (3 files)
tasks and services: build, deploy, more:lint
from: path=.hammerkit.yaml repo=github.com/corp/payments commit=4be1a07c... machine=ci-runner-7 user=runner
```

It reads the build file with the parser of a run and sends it together with every
local file it includes or references, as text. That is the bundle, up to 200 files
and 1 MiB. Includes have to be below the directory of the build file, because a
server could not reproduce anything else; git includes are not sent, the server
fetches them and wants them pinned to a commit. The version printed is the hash of
the bundle, computed here the same way the server computes it, so the same files
always have the same version. That hash is the only name the version has: a run
names it, there is no `latest`. Publishing what a server already has says `already
published` and changes nothing.

With the bundle go [annotations](/docs/remote-compute/build-files#annotations) that say
where it comes from, the `from:` line: the path of the build file in its git repository,
the repository and commit, this machine and your user name. When a file of the bundle is
not as the commit has it (changed, or not committed at all), `dirty=true` says so, so the
version is not taken for that commit's. They are not part of the hash. `--annotation key=value` adds one or replaces one, `--annotation user=` leaves one
out, and it can be given more than once. `remote versions` lists what a server has and
finds it by them, and `remote show <hash>` prints one whole. Anybody else sees them as
`from (unverified)`, since the server takes them as you sent them:

```
$ hammerkit remote versions build --filter repo=github.com/corp/payments
build: 1 published
sha256:9f2c61d0...  published by ci at 2026-10-12T20:31:00.000Z
  from (unverified): path=.hammerkit.yaml repo=github.com/corp/payments commit=4be1a07c... machine=ci-runner-7 user=runner
  tasks and services: build, deploy, more:lint
  accounts: op-payments-prod
```

You need `builds: publish` on the server, see
[entitlements](/docs/remote-compute/entitlements). A build file that reads secrets as an
account you do not `use` is proposed instead, see below. Without a server name the default
server is used, and `--file <path>` publishes another build file.

### Proposing a version

With only `builds: propose`, or when the build file names an account you do not use,
the same command proposes the version. It does not become a version and can not run
until somebody who may publish, and uses those accounts, approves it:

```
$ hammerkit remote publish build
proposed to build: sha256:4be1a07c... (3 files)
tasks and services: build, deploy, more:lint
it can not run before somebody who may publish approves it, until 2026-10-11T11:41:00.000Z
```

The one who may publish reads the whole version before deciding:

```
$ hammerkit remote proposals build
build: 1 proposed
sha256:4be1a07c...  proposed by coding-agent, waits for your approval
  from (unverified): path=.hammerkit.yaml repo=github.com/corp/payments machine=agent-sandbox-3 user=agent
  tasks and services: build, deploy, more:lint
  accounts: op-payments-prod, the proposer does not use op-payments-prod
  decide before 2026-10-11T11:41:00.000Z
$ hammerkit remote show sha256:4be1a07c... build
sha256:4be1a07c... on build, proposed by coding-agent (https://login.example.com), waiting
  deploy  task, docker node:22
    $ ./deploy.sh
    after: build
    secret gsm:kube-token as op-payments-prod -> KUBE_TOKEN
  ...
--- .hammerkit.yaml (entry)
  tasks:
    build:
      cmds: [npm run build, ./upload.sh]
  ...
$ hammerkit remote approve sha256:4be1a07c... build
approved sha256:4be1a07c... on build, it is published
```

`remote show` prints what each task does and then every file of the bundle, whole and
with control characters replaced by `?`, so nothing hides in it. It does not compare
with an earlier version: a version has no name and follows none, so a diff would only
show what the proposer chose to compare with. `remote reject` drops the proposal, with a
`--reason` the one who proposed it reads in `remote proposals`. Nobody approves their
own proposal, and what you may not decide does not exist for you. After a rejection you
can not propose again for ten minutes, and nobody that version (`approvals.cooldown`).

## Running tasks

`remote run` starts a run of a published version on a server, from a branch or tag of
your repository that the server checks out itself, and follows it to its end:

```
$ hammerkit remote run test --server build
run_Qx3k9ZpL2mW7vN4a on build: test from main at 4be1a07c...
[hammerkit] checked out github.com/corp/payments at 4be1a07c...
 ✓ 42 tests passed
run_Qx3k9ZpL2mW7vN4a succeeded
```

It prints every line of the run as the server logs it, with the task in front when the line
is not of the one task you named (`[hammerkit]` is the server's own, so a task of that name
is best called something else). It exits with `0` when
the run succeeded and with the exit code of the task that failed otherwise, `1` when the
run was rejected, cancelled or failed without one. Control characters of the output show as
`?`, so the output of a run can not rewrite your terminal; tabs stay.

What it runs, when you leave the options out, is what is checked out where you are:

| Option | What it is | Left out |
| --- | --- | --- |
| `--build <hash>` | The published version to run, also `HAMMERKIT_BUILD`. | The hash of the build file here (or the one `--file` names), computed as `remote publish` does. A build file that is not published fails with `publish it first`. |
| `--repo <host/path>` | The repository, such as `github.com/corp/payments`. The server reads it from its own [sources](/docs/remote-compute/sources). | The `origin` of the checkout. |
| `--ref <ref>` | The branch or tag. | The branch checked out here. A detached checkout has none, name it then. |
| `--commit <sha>` | The commit the ref has to be at. A ref that moved since is refused, so the run executes the code you meant: `main is at 9e1f... now, not at 4be1a07c...`. | The commit checked out here when `--ref` is left out too, else no pin. |
| `--server <name>` | The server. | The default of `remote use`. |
| `--env`, `--cache`, `--timeout` | As for [`run`](/docs/remote-compute/runs#submitting-a-run). | The server's and the build file's defaults. |

What follows `--` goes to the one task named, as the
[arguments](/docs/remote-compute/runs#arguments) of a run. The server refuses them for a
task that reads a secret or depends on one that does.

A run on an account you may only `request` waits for an approval, and says so:

```
waiting until somebody who uses deploy-prod approves it, before 2026-10-24T10:41:00.000Z: hammerkit remote approve run_Qx3k9ZpL2mW7vN4a
```

The command waits as long as the server lets the run wait (`approvals.timeout`, one hour by
default). Ctrl-C, or the cancel of a CI job, cancels the run on the server: the command waits
up to ten seconds for the server to take the cancel before it ends. The token is the one of
[Signing in](#signing-in), or `HAMMERKIT_TOKEN_COMMAND` / `HAMMERKIT_TOKEN`, which is how a CI
job signs in with its own identity, see
[CI through a server](/docs/guides/agents/github-actions).

## Approving runs

A run that reads secrets as a service account its caller may only
[request](/docs/remote-compute/entitlements#approvals) waits for somebody who uses that account to
approve it. If you use the account:

```
$ hammerkit remote approvals build
build: 1 waiting for your approval
run_Qx3k9ZpL2mW7vN4a  requested by 4f1c2b (https://login.example.com)
  build file sha256:9f2c61d0...
  tasks: deploy
  accounts: op-payments-prod, source ref refs/heads/main, env=staging
  op-payments-prod: waits for somebody who uses it to approve
  decide before 2026-10-11T10:41:00.000Z
$ hammerkit remote approve run_Qx3k9ZpL2mW7vN4a build
approved run_Qx3k9ZpL2mW7vN4a on build, it is queued
```

`remote show` prints what each task of the run does, so the decision does not need the
build file:

```
$ hammerkit remote show run_Qx3k9ZpL2mW7vN4a build
...
  deploy  task, docker node:22  [remote-include]
    $ ./deploy.sh
    after: build
    secret gsm:kube-token as op-payments-prod -> KUBE_TOKEN
```

The line `look at:` of the list names the tasks with a flag: `local-task` runs on the host
and not in a container, `host-port` binds a port of the host and `remote-include`
includes a file from git. A secret's value is never shown, only where it is read from.

A run that passes [arguments](/docs/remote-compute/runs#arguments) uses no account, so it
waits for nobody; one stored before that rule lists them on a line of their own, each as a
JSON string (`arguments: "--region" "eu, us"`). `remote show` prints each command as it
runs. Arguments and commands are never cut; other text longer than 300 characters ends in `… (+N chars)`. Control
characters show as `?`, and bidi and zero-width characters are written out
(`\u{202e}`), so what you read is the order it runs in. A task that isn't `open` shows
its `network`.

What you see is what the decision rests on: who asked, which version of the build
file, the tasks, the service accounts they read secrets as and where the code comes
from. The version is the one the run is pinned to, so what you approve is what runs.
You approve for every account you use; a run on several waits until they are all
covered. You see the runs on the accounts you use, and no others.

## Signing in

`remote login` uses the OAuth device authorization grant, so it works on a machine
without a browser:

```
$ hammerkit remote login build
signing in to https://build.example.com through https://login.example.com
  client hammerkit-cli, audience hammerkit, scope openid api://hammerkit/.default
To sign in, open https://login.example.com/activate and enter the code ABCD-EFGH
signed in to build as 4f1c2b
service accounts: op-payments-dev (use), op-payments-prod (request), op-web-dev (use)
```

Open the address on any device, sign in as you normally do, and enter the code. The
server tells hammerkit which identity provider client, audience and scope to use, so
there is nothing to configure beyond `remote add`. The `--issuer` you registered has to be one the
server accepts, otherwise the login stops before the browser step.

The server is only trusted with that once. The first successful login pins the client,
audience and scope in the host config, and a later login refuses a server that asks
for something else (register it again with `remote add --force` if the change is
expected). Look at the line printed before the code: a client or audience you do not
recognise, such as one of a cloud provider's own APIs, means stop. To not rely on the
first use, give them to `remote add` (`--client-id`, `--audience`, `--scope`), the
values come from whoever runs the server. Before a token is sent to the server,
hammerkit checks that it was issued by the registered issuer for the pinned audience,
so a token for another service never leaves your machine. `offline_access` is dropped
from the scope: no refresh token is requested.

What is stored is one short-lived access token in `~/.hammerkit/credentials.json`
(`HAMMERKIT_CREDENTIALS` picks another file), readable by you only (a file others can read is not used; hammerkit says how to fix it). A refresh token
is not kept: when the token expires, `remote login` again. The token is bound to the
URL and issuer it was issued for, so registering the name again for another server
(`remote add --force`) does not send the old token there.

Agents and CI do not use `login`. They bring their own token, an agent from its own
client credentials and a CI job from the OIDC token of the job, and the server maps
it to service accounts through its [entitlements](/docs/remote-compute/entitlements).
The `remote` commands take such a token instead of a sign-in, in this order:

| Variable                  | What it is                                                                                                                      |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `HAMMERKIT_TOKEN_COMMAND` | A command that prints the token, run for each command, such as a script that asks the identity provider for a service account. |
| `HAMMERKIT_TOKEN`         | The token itself, as a CI job gets it.                                                                                          |

```yaml title=".gitlab-ci.yml"
publish:
  id_tokens:
    HAMMERKIT_TOKEN:
      aud: hammerkit
  script:
    - hammerkit remote add build https://build.example.com --issuer https://gitlab.com
    - hammerkit remote publish build
```

The token goes only to the server the name is registered for.
