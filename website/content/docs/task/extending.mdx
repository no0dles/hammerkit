---
title: "Extending"
description: "A task can be used as a base template and extended. This is intended to reduce duplicate task definitions."
---
Extending tasks avoids a lot of duplicated task definitions in bigger projects and monorepos. With the `extend` property, a task uses another task's configuration as a template.

The following sections and examples use the two predefined tasks in the `build.tsc.yaml` file — one of the ready-made templates shipped under
[`best-practices/`](https://github.com/no0dles/hammerkit/tree/master/best-practices). Copy it into your project (or include it directly) to follow along.

```yaml title="build.tsc.yaml"
tasks:
  install:
    src:
      - package.json
      - package-lock.json
    generates:
      - node_modules
    cmds:
      - npm ci
      
  build:
    deps: [ install ]
    src:
      - tsconfig.json
      - src
    cmds:
      - node_modules/.bin/tsc
    generates:
      - dist
```

### Extend a task

Extending `tsc:build` uses all of its properties as a base. If nothing else is defined, the result is an exact copy that runs in the working directory of the current build file.

```yaml title=".hammerkit.yaml"
tasks:
  build:
    extend: tsc:build
    
includes:
  tsc: ./build.tsc.yaml
```

### Override properties in an extend

An extending task can override any property, whether the base defines it or not. Single
values such as `image`, `shell`, `cache` and `timeout` are replaced by the extending
task's own value. Lists and maps are **added to** the base's instead:

| Property | With `extend` |
|---|---|
| `image`, `shell`, `cache`, `timeout` | The task's own value replaces the base's. |
| `cmds`, `src`, `generates`, `mounts` | The base's entries come first, the task's own follow. |
| `deps`, `needs` | Both are used. |
| `envs`, `labels` | Merged. The task's own value wins for a name both define. |

The `envs` of the base also include the top-level `envs` of the build file it comes from,
so a base that reads `$NODE_VERSION` keeps its default when you extend it.

```yaml title=".hammerkit.yaml"
tasks:
  build:
    extend: tsc:build
    src:
      - ../../tsconfig.base.json
    
includes:
  tsc: ./build.tsc.yaml
```

Here `build` runs the base's commands against the base's sources plus
`../../tsconfig.base.json`.

### Reset inherited values

To take nothing from the base for a property, name it in `reset`. The task's own value for
that property still applies. In this example the dependencies are cleared, so the task runs
without depending on `install`:

```yaml title=".hammerkit.yaml"
tasks:
  build:
    extend: tsc:build
    reset: [deps]
    
includes:
  tsc: ./build.tsc.yaml
```

`reset` accepts `deps`, `needs`, `src`, `generates`, `cmds`, `mounts`, `envs` and `labels`.
It is an error without `extend`. An empty `deps: []` does not clear the base's
dependencies, because the lists are added together.

### Naming the base task

`extend` uses the same `<prefix>:<task>` addressing as [dependencies](/docs/task/dependencies):
the part before the colon is the [include](/docs/build-file/includes) (or
[reference](/docs/build-file/references)) prefix, and the part after it is the task
name in that file. `extend: tsc:build` means "the `build` task from the file
included as `tsc`". To extend a task in the *same* file, use its bare name
(`extend: build-base`).
