</Callout>

A coding agent needs to read, edit and search files and to run commands. On a
[sandbox](/docs/remote-compute/sandboxes) the files stay on the server and the commands run
there, as published tasks in their containers. hammerkit connects agents to it three ways:

| Client                                          | What it gets                                                                                                      |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| [`hammerkit remote mcp`](#hammerkit-remote-mcp) | MCP tools for any client that speaks MCP: Claude Code, Claude Desktop, Cursor, a custom agent.                    |
| [pi](#pi)                                       | pi's own `read`, `write`, `edit`, `bash`, `ls`, `find` and `grep`, working on the sandbox.                        |
| [opencode](#opencode)                           | opencode's own `read`, `write`, `edit`, `apply_patch`, `bash`, `grep`, `glob` and `list`, working on the sandbox. |

pi and opencode keep the tools their models are tuned for, with the same names, parameters
and output: only where they read, write and run moves. The MCP tools take the shapes models
are trained on: numbered reads with an offset and limit, an exact string replace, an
`apply_patch` body or a git diff, ripgrep's parameters and a shell command.

## The shell task

There is no command endpoint on the server: commands bypassing the published build file
would bypass its image, network and accounts. A shell is a published task whose last command
is a shell, and every command of the agent is its [argument](/docs/task/arguments):

```yaml title=".hammerkit.yaml"
tasks:
  sh:
    image: node:24
    cmds: [sh -c]
    network: { allow: [registry.npmjs.org] }
```

`bash` with `npm test -- -t login` then runs `sh -c 'npm test -- -t login'` in that image,
on the files of the sandbox. Name the task `sh` or tell the client its name. Use `bash -c`
when the image has bash. A task that reads secrets takes no arguments on a server, so the
shell holds no account. Its network is the lower of its own `network`,
[`runs.network`](/docs/remote-compute/runs#config) and
[`sandboxes.network`](/docs/remote-compute/sandboxes#config).

What follows from running a command as a task:

- Commands run one at a time, each in a fresh container: only the files are kept between
  them. A background process ends with its command, and `cd` or `export` in one command does
  not reach the next. The clients run a command in a directory with `cd <dir> || exit 1` on a
  line before it.
- The command reads no input and gets none of the agent's variables.
- While a command runs, the sandbox is held: an edit in the meantime is `409`.
- What it printed comes from the [log of the run](/docs/remote-compute/runs#logs). A long
  log is cut at `runs.maxLogBytes`; the last lines of the task are kept past it.

## Sign-in

The clients send the token of the agent, not of a person, to the server registered in the
host config ([`hammerkit remote add`](/docs/cli/remote)), and nowhere else. They look for it
in this order:

| Source                            | What it is                                                                                                                                                                                                                                                                   |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `HAMMERKIT_TOKEN_COMMAND`         | A command that prints a short-lived access token of the agent's own identity, for example a service account or workload identity of the identity provider the server accepts. It runs again when the server stops accepting the token, so a long session outlives one token. |
| `HAMMERKIT_TOKEN`                 | Such a token, as the agent's platform hands it over.                                                                                                                                                                                                                         |
| `hammerkit remote login <server>` | The sign-in stored on the machine, for an agent a person starts on their own machine.                                                                                                                                                                                        |

Give the agent's identity an [entitlement](/docs/remote-compute/entitlements) with its
repositories and branches under `sandboxes`, `builds: run`, and no account that holds
production secrets. `[{ repo: github.com/corp/*, branches: { main: pull, "agent/**": push } }]`
lets it start from `main` and push to `agent/**`; with only `pull` it hands back patches.

## Settings

All three clients take the same settings, `hammerkit remote mcp` as options too:

| Variable                          | Option            | What it names                                                                                                                                                                                                                                                                                                                                                                                |
| --------------------------------- | ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `HAMMERKIT_SERVER`                | `--server`        | The registered server. Default: the one `hammerkit remote use` set.                                                                                                                                                                                                                                                                                                                          |
| `HAMMERKIT_SANDBOX`               | `--sandbox`       | A sandbox of the agent, for example `sbx_4vJ0mT2cX9qLw1aB`.                                                                                                                                                                                                                                                                                                                                  |
| `HAMMERKIT_REPO`, `HAMMERKIT_REF` | `--repo`, `--ref` | Instead of a sandbox: one of this repository at this branch. When the client starts, it takes a sandbox of yours of the same repository and branch that has no changes and checks it out at the branch again, or creates one. A sandbox stays until it is deleted and the server allows only a few, so set `HAMMERKIT_SANDBOX` to the id the client prints to come back to work in progress. |
| `HAMMERKIT_BUILD`                 | `--build`         | The published build file whose tasks run on the sandbox.                                                                                                                                                                                                                                                                                                                                     |
| `HAMMERKIT_SHELL`                 | `--shell`         | Its shell task, `sh` by default.                                                                                                                                                                                                                                                                                                                                                             |

## hammerkit remote mcp

[`hammerkit remote mcp`](/docs/cli/remote-mcp) is an MCP server on stdio for one sandbox.
Clients start it as a command:

```json title=".mcp.json"
{
  "mcpServers": {
    "hammerkit": {
      "command": "npx",
      "args": ["hammerkit", "remote", "mcp", "--server", "corp", "--build", "payments"],
      "env": { "HAMMERKIT_SANDBOX": "sbx_4vJ0mT2cX9qLw1aB", "HAMMERKIT_TOKEN_COMMAND": "agent-token" }
    }
  }
}
```

Paths are relative to the root of the sandbox. The tools:

| Tool          | Parameters                                                                                                           | What it does                                                                                                                                                                                  |
| ------------- | -------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `read`        | `path`, `offset`, `limit`                                                                                            | The lines of a file, numbered like `cat -n`, in parts for long files.                                                                                                                         |
| `write`       | `path`, `content`                                                                                                    | Writes a whole file, making its directories.                                                                                                                                                  |
| `edit`        | `path`, `old_string`, `new_string`, `replace_all`                                                                    | Replaces a string that matches exactly once, or every match.                                                                                                                                  |
| `apply_patch` | `patch`                                                                                                              | A `*** Begin Patch` body or a git diff; every file changes or none.                                                                                                                           |
| `search`      | `pattern`, `path`, `glob`, `type`, `-i`, `-A`, `-B`, `-C`, `fixed_strings`, `multiline`, `output_mode`, `head_limit` | ripgrep on the server.                                                                                                                                                                        |
| `glob`        | `pattern`, `path`                                                                                                    | The files that match a glob.                                                                                                                                                                  |
| `bash`        | `command`, `workdir`, `timeout` (seconds)                                                                            | Runs a command as the shell task and answers its output and exit code. A long output keeps its first 50 and last 200 lines, about 30 KB; `run_logs` reads the rest.                           |
| `run_task`    | `task`, `args`                                                                                                       | Runs another published task, such as `test`, and answers its [result](/docs/remote-compute/runs#results-and-waiting): status, exit code, why it was not taken from the cache, its last lines. |
| `run_logs`    | `run`, `task`, `tail`, `from`, `limit`, `grep`, `ignore_case`, `context`                                             | Reads more of the [log of a run](/docs/remote-compute/runs#logs).                                                                                                                             |
| `changes`     | `format`: `summary`, `diff` or `patch`                                                                               | What changed since the sandbox was fetched.                                                                                                                                                   |

Reads and searches are marked `readOnlyHint`, the edits `destructiveHint`; `bash` and
`run_task` keep the defaults, since a command can do anything its task can. The server
also tells the client which sandbox, repository and commit the tools work on.

## pi

hammerkit is a [pi package](https://pi.dev/packages): installing it adds the extension.

```bash
pi install npm:hammerkit
HAMMERKIT_SERVER=corp HAMMERKIT_BUILD=payments HAMMERKIT_SANDBOX=sbx_4vJ0mT2cX9qLw1aB pi
```

The extension registers pi's own `read`, `write`, `edit`, `bash`, `ls`, `find` and `grep`
with the sandbox as their backend, the way pi's SSH example does, and runs the user's `!`
commands there too. pi's working directory stands for the root of the sandbox: a path below
it is the same path in the sandbox, anything else is refused. The system prompt names the
sandbox, so the model knows nothing is installed on the machine. `grep` searches with
ripgrep on the server. Images are read from the sandbox like any file.

## opencode

opencode lets a plugin replace a built-in tool by registering one of the same name. Add
hammerkit to the dependencies of the project's opencode directory and re-export its plugin:

```json title=".opencode/package.json"
{
  "dependencies": { "hammerkit": "^1", "@opencode-ai/plugin": "*" }
}
```

```ts title=".opencode/plugins/hammerkit.ts"
export { HammerkitPlugin } from 'hammerkit/harness/opencode'
```

Then start opencode with the [settings](#settings) as variables. The tools take opencode's
parameters (`filePath`, `oldString`, `newString`, `replaceAll`, `patchText`, `workdir`,
`timeout` in milliseconds) and answer in its words, and opencode still picks `apply_patch`
for GPT models and `edit` and `write` for the others. opencode's directory stands for the
root of the sandbox. A long `bash` output keeps its first and last lines, like the MCP tool.

Tools the plugin does not replace still work on the machine opencode runs on. Turn off the
ones that touch local files and that your opencode version still has, for example
`"tools": { "multiedit": false }` in `opencode.json`.

## What is not covered yet

- Pushing a branch from the sandbox: take the work out with `changes` as a patch.
- A service on the sandbox, such as a dev server to send requests to.
- Commands that read input, and long-running background commands.
