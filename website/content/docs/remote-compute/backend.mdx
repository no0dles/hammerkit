---
`backend` says where the tasks of runs execute. `host` is this machine, with the same engine
as `hammerkit run`. `kubernetes` runs them as Jobs on a cluster, see [Kubernetes](#kubernetes).
`runtimes` says which runtimes of the engine tasks may use.

```yaml title="server.yaml"
backend:
  type: host
  platform: { os: macos, arch: arm64 }   # detected when left out
runtimes: [docker]   # what tasks may run on, docker by default
```

| Key | What it does |
| --- | --- |
| `backend.type` | `host` (this machine, the default) or `kubernetes` (a cluster). |
| `backend.platform` | `host` only. What the machine offers: `os` is `linux`, `macos` or `windows`, `arch` is `amd64` or `arm64`. Detected when left out. Clients read it from the [discovery document](/docs/remote-compute#discovery). |
| `runtimes` | What tasks may run on, see [Runtimes](#runtimes). |

## Runtimes

`runtimes` lists what tasks may run on: `docker` (containers, the default) and `local`
(commands on this machine as the user of the server, which have to be allowed by name).

```yaml title="server.yaml"
runtimes: [docker, local]
```

A build file with a task on a runtime that is not listed is refused when it is published
or proposed, see [What a build file may not do](/docs/remote-compute/build-files#what-a-build-file-may-not-do).
The server logs a warning at startup when `local` is allowed on a host. A container task uses the
docker daemon of the server's environment, so name `DOCKER_HOST` in
[`runs.env.allow`](/docs/remote-compute/runs#config) when it is not the default.

On a cluster `local` means a task without an image runs in the `toolImage` of a pool, see
[Pools](#pools).

## One server is one trust level

On a host, the process of a run is not a sandbox. It runs as the user
of the server, a `local` task reads everything that user can read, and a container task can
use the docker daemon the server is configured for. Accounts keep credentials apart (a task
only reads the secrets of the accounts its run was admitted for), but they do not keep code
apart on one machine. Do not mix production and untrusted agents on one server: run
them on different servers, each with the accounts of its own level, and with `local` only on
a server whose users you trust with the machine. The storage directory and the other runs of
a server are inside what a `local` task can read.

On a cluster every task is a pod of its own in the caller's namespace, without a token of the
cluster. The boundary is the container, the namespace and the network policies the server puts
in it (see [Namespaces](#namespaces)), which only hold on a network plugin that enforces
`NetworkPolicy`. Keep the server off the nodes of the pools, so a task that escapes its
container does not share a node with the server's token. The server still holds the
right to mint the tokens of every account (see [Secrets in the Job](#secrets-in-the-job)), so
the advice stands: one server, and one set of accounts, per trust level.

## Kubernetes

<Callout type="warn">
Experimental, like the server. Linux nodes only.
</Callout>

```yaml title="server.yaml"
backend:
  type: kubernetes
  namespace: hammerkit              # the server's own; the namespace of its pod when left out
  # kubeconfig: /etc/hammerkit/kubeconfig   # with context, for a cluster the server is not in
  # context: prod
  storageClass: standard-rwo        # of the claims of tasks; the cluster's default when left out
  pools:
    - name: builds
      platform: { os: linux, arch: amd64 }
      nodeSelector: { cloud.google.com/gke-nodepool: builds }
      tolerations: [{ key: builds, operator: Exists, effect: NoSchedule }]
      toolImage: ghcr.io/corp/build-tools:2026.10
  providers:
    gsm: { image: gcr.io/google.com/cloudsdktool/google-cloud-cli:slim }
  quota: { requests.cpu: '8', requests.memory: 16Gi, persistentvolumeclaims: '20' }
  defaultResources: { requests: { cpu: 250m, memory: 256Mi } }
  sandboxes: { size: 4Gi, storageClass: sandboxes }
  # runRole: hammerkit-runs           # the ClusterRole the server binds in each caller's namespace
  deniedEgress: [169.254.0.0/16, fe80::/10, fd00:ec2::/32, 10.0.0.0/8]   # the default, and the cluster's ranges
  networkPolicy: enforced            # the network plugin enforces NetworkPolicy; limited tasks need it
```

The server runs as before (it checks the code out, plans the run with the engine in a process
of its own and keeps the cache), but every container task of a run becomes a Job and every
service a Deployment, in a namespace of the caller.

| Key | What it does |
| --- | --- |
| `namespace` | The server's own namespace, where the [credentials of the accounts](#secrets-in-the-job) are. Found on its own when the server runs in a pod. |
| `kubeconfig`, `context` | The cluster, for a server outside of it. Without them the server uses its default kubeconfig, else the cluster it runs in. |
| `namespacePrefix` | A caller's namespace is this and the first 16 hex digits of the sha-256 of their issuer and subject, `hammerkit-` by default. Two servers on one cluster need a prefix each. |
| `storageClass` | The storage class of the claims tasks get. |
| `pools` | Where pods are placed, see [Pools](#pools). One `linux`/`amd64` pool when left out. |
| `providers` | Per secret provider, the image its command runs in. Every provider an account reads needs one. |
| `quota` | The `ResourceQuota` of each caller's namespace, as Kubernetes writes it (`requests.cpu`, `limits.memory`, `pods`, `persistentvolumeclaims`, `requests.storage`). |
| `defaultResources` | `requests` and `limits` (`cpu`, `memory`) for containers without [`resources`](/docs/task#resources), as a `LimitRange`, so they are admitted under a quota that limits compute. |
| `sandboxes` | Where [sandboxes](/docs/remote-compute/sandboxes#on-kubernetes) are kept: two claims per sandbox in its caller's namespace, their size and storage class, and the image and resources of the pod that reads and edits its files. |
| `runRole` | The ClusterRole the server binds to itself in each caller's namespace, `hammerkit-runs` by default, see [What the server may do](#what-the-server-may-do). |
| `deniedEgress` | Address ranges a pod of a run with an open network may not connect to. By default the link-local ranges, where the clouds' metadata endpoints hand out the node's identity (`169.254.0.0/16`, `fe80::/10`, `fd00:ec2::/32`). Add the pod and service ranges of the cluster to keep tasks off its other workloads, the server's included. |

### Namespaces

The first run of a caller makes their namespace, labelled `hammerkit.dev/managed`. A namespace
of that name without the label is refused, the server runs no task in a namespace it did not
make. On every run the server puts in it, replacing what was there:

- a RoleBinding of `runRole` to itself, its only rights in the namespace;
- a `NetworkPolicy` that lets each pod with an open network accept connections from the pods of
  its namespace only (the services a task needs), so callers can not reach each other's pods;
- a `NetworkPolicy` for the pods with an open network and the egress proxies: they reach their
  namespace, DNS and any address outside `deniedEgress`.

Policies add up, so neither selects a pod with a limited [network](#network) (labelled
`hammerkit.dev/network: limited`): its own policy alone decides what it reaches, DNS left out, and
what reaches it. An egress proxy takes connections from its task only.
- `quota` and `defaultResources`; removing one from the config removes it from the namespace.

The namespace enforces the `baseline` [Pod Security Standard](https://kubernetes.io/docs/concepts/security/pod-security-standards/):
no privileged pods, host paths or host network. Every container of a run runs with
`allowPrivilegeEscalation: false` (so `sudo` and other setuid programs do not work), without
the `NET_RAW` capability (no `ping`) and with the runtime's seccomp profile, and without a token
of the cluster.

What a run makes there carries the label `hammerkit.dev/run` and is deleted when the run ends,
whether it succeeded or not, and the end of the run waits until its pods and claims are gone:
an idle caller costs nothing on the cluster. What a run left because the server stopped before
its end is deleted when the caller's next run starts. The runs of one caller execute one after
the other, since the Jobs and claims of a task are named after its cache id; the next waits in
the queue, without counting against `runs.maxDuration`. The runs of different callers run side
by side. A pod that does not fit the nodes waits for one, and a pod over the quota is not
created until the quota has room: the task waits in both cases, until `runs.maxDuration`.

### Pools

A pool is a set of nodes: `platform` (`linux`, with `amd64` or `arm64`), `nodeSelector`
(the labels besides `kubernetes.io/os` and `kubernetes.io/arch`, which come from `platform`)
and `tolerations`. Container tasks and services go to the first pool. A task without an image
runs in the `toolImage` of the first pool that has one and offers the `platform` the task
declares (`platform: { arch: arm64 }` picks an `arm64` pool). A task for macOS or
Windows has no pool and fails when the run starts. `runtimes` has to list `local` for such tasks,
and at least one pool needs a `toolImage` then.

### Secrets in the Job

The server reads no secret of a provider for a task on a cluster: the Job of the task does,
with only the credentials of the accounts it uses. Each provider secret gets an init container
in the provider's image, which runs the provider's command with the provider's and the account's
`env` and writes the value into a volume in memory. The task's container mounts only that
volume: a `path:` secret is the file, an `env:` secret is set before the command runs.

The credential of an account is set under `accounts.<name>.kubernetes` and is put at
`/var/run/hammerkit/account/` in the init containers of that account only:

```yaml title="server.yaml"
accounts:
  payments-dev:
    providers:
      gsm: { env: { CLOUDSDK_AUTH_CREDENTIAL_FILE_OVERRIDE: /var/run/hammerkit/account/gcp.json } }
    kubernetes:
      serviceAccount: payments-dev    # a ServiceAccount in backend.namespace
      audience: //iam.googleapis.com/projects/123/locations/global/workloadIdentityPools/hk/providers/cluster
      secret: payments-dev-federation # a Secret in backend.namespace, each key a file
```

| Key | What it does |
| --- | --- |
| `serviceAccount` | A ServiceAccount of the server's namespace. Right before each Job of the task, the server asks for a token of it (an hour, for `audience`) and puts it at `token`; the Secret that carries it is deleted when the Job is done. A cloud that trusts the cluster's issuer for that ServiceAccount (GCP workload identity federation, AWS `AssumeRoleWithWebIdentity`, Azure federated credentials) exchanges it for the account's credentials. Short-lived, and one trust binding per account whoever the caller is. |
| `audience` | The audience of that token; the cluster's default when left out. |
| `secret` | A Secret of the server's namespace, each key a file of the directory: the federation config that points at `token`, or a key file where nothing else works (long-lived, so the second choice). |

On a cluster every account with `providers` needs `kubernetes`, or the server does not start:
its commands would otherwise run as whatever identity the node or the provider's image has,
the same for every account.

The values never reach the server, so it can not mask them in the log. The task's output is
masked in the pod instead, with `awk`, line by line, before it leaves the pod: the image of a
task that reads such a secret needs `awk` (busybox, alpine, debian and their kin have it), and
stdout and stderr arrive as one stream. Encodings of a value (base64, hex) are not masked
there. `env:` secrets (variables of `runs.env.allow`) are the server's own and are handed over
as before.

Not yet on a cluster, and refused when a build file is published: a provider secret on a
service, and a provider secret with `cache: true` (its digest would be needed before the Job
reads the value).

### Cache and sources

The cache stays on the server, one per source trust as on a host (a repository's runs share it).
After a task ran, its outputs are copied from its claim into the cache, and a later run that
hits restores them into a new claim before its dependents start. The files of a task's `src`
are copied from the server's checkout into its claim. So on a cluster the storage directory
of the server (`storage.directory`) belongs on a volume of its own.

### Network

A task's [`network`](/docs/task/network) works on a cluster as in a
[Kubernetes environment](/docs/task/network#kubernetes): a limited task's Jobs get a `NetworkPolicy`
that lets them reach only the services they need and, under `allow`, their egress proxy, a
Deployment on the first pool. A task without an image takes no `network` of its own yet (the
build file is refused when it is read), but a run's `--network` ceiling limits it like a
container task, since it runs in a container of the tool image. The policy, the proxy and its
Service carry `hammerkit.dev/run` and go with the rest of the run. Pods with an open network are
governed by the policy of the caller's namespace, see [Namespaces](#namespaces).

The cluster's network plugin has to enforce `NetworkPolicy` (Calico and Cilium do, and recent
kind), for `network:` and for keeping callers apart. Without it nothing is isolated. Hammerkit
can't tell from the API, so `backend.networkPolicy: enforced` states it; without it a task with a
limited network fails instead of running open. With
[sandboxes](/docs/remote-compute/sandboxes#on-kubernetes), whose runs are limited by
`sandboxes.network`, a config without it is refused unless that is `open`. Some apply a
policy a moment after the pod started, so a limited pod waits in an init container until its
policy holds, and fails after 60 seconds if it never does (see
[Kubernetes](/docs/task/network#kubernetes)). A run's policies go only after its pods are gone.
A pod with an open network has no such wait, so on those plugins it can reach a `deniedEgress`
address in its first moment.

A task that reads a provider's secret keeps an open network for now: its init containers are in
the task's pod, so its policy would cut them off from the secret manager. Such a build file is
refused when it is published, and a run whose ceiling would limit such a task fails that task.

### Sandboxes

A [sandbox](/docs/remote-compute/sandboxes#on-kubernetes) is two claims in its caller's
namespace, next to the namespace's runs: its files, and its git data. A short pod of
`backend.sandboxes.image` fetches into them, reads and edits the files and commits what the
server pushes; the Jobs of a run on the sandbox mount the files only. The quota of sandboxes
is a `ResourceQuota` on their storage class, when they have one of their own. The pod runs as
root with only the capabilities to own and change files (the `baseline` Pod Security level
allows it, `restricted` does not).

### What the server may do

Across the cluster the server makes namespaces and binds `runRole` in the ones it made. With
[sandboxes](#sandboxes) it also lists namespaces when it starts, to find the claims of sandboxes
in the ones it made. It needs
no rights on Secrets or pods outside of them: those come from `runRole`, which it binds in each
caller's namespace (Kubernetes lets it bind that role only, by `bind`). In its own namespace it
reads the Secrets of the accounts and makes tokens of their ServiceAccounts, by name. The
processes of runs use the same identity.

```yaml title="rbac.yaml"
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata: { name: hammerkit-server }
rules:
  - { apiGroups: [''], resources: [namespaces], verbs: [get, list, create] }   # list: with sandboxes
  - { apiGroups: [rbac.authorization.k8s.io], resources: [rolebindings], verbs: [get, create, update] }
  - apiGroups: [rbac.authorization.k8s.io]
    resources: [clusterroles]
    verbs: [bind]
    resourceNames: [hammerkit-runs]
---
# bound by the server in each caller's namespace, never across the cluster
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata: { name: hammerkit-runs }
rules:
  - { apiGroups: [''], resources: [resourcequotas, limitranges], verbs: [get, create, update, delete] }
  - apiGroups: ['']
    resources: [pods, pods/exec, pods/log, persistentvolumeclaims, secrets, services]
    verbs: [get, list, create, patch, delete, deletecollection]
  - apiGroups: [batch]
    resources: [jobs, jobs/status]
    verbs: [get, list, create, patch, delete, deletecollection]
  - { apiGroups: [apps], resources: [deployments], verbs: [get, list, create, patch, delete, deletecollection] }
  - apiGroups: [networking.k8s.io]
    resources: [networkpolicies]
    verbs: [get, list, create, update, patch, delete]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { name: hammerkit-accounts, namespace: hammerkit }
rules:
  # the secret and serviceAccount of each account
  - { apiGroups: [''], resources: [secrets], verbs: [get], resourceNames: [payments-dev-federation] }
  - { apiGroups: [''], resources: [serviceaccounts/token], verbs: [create], resourceNames: [payments-dev] }
```
Bind `hammerkit-server` with a ClusterRoleBinding and `hammerkit-accounts` with a RoleBinding to
the server's ServiceAccount; do not bind `hammerkit-runs` yourself. Making RoleBindings across the
cluster still lets the server bind `hammerkit-runs` in a namespace it did not make. To rule that
out, admit its RoleBindings in managed namespaces only:

```yaml title="admission.yaml"
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata: { name: hammerkit-managed-namespaces }
spec:
  matchConstraints:
    resourceRules:
      - { apiGroups: [rbac.authorization.k8s.io], apiVersions: ['*'], operations: [CREATE, UPDATE], resources: [rolebindings] }
  matchConditions:
    - { name: server, expression: "request.userInfo.username == 'system:serviceaccount:hammerkit:hammerkit'" }
  validations:
    - expression: "namespaceObject.metadata.?labels['hammerkit.dev/managed'].orValue('') == 'true'"
---
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata: { name: hammerkit-managed-namespaces }
spec: { policyName: hammerkit-managed-namespaces, validationActions: [Deny] }
```

Not yet: Windows nodes, holding a pod with an open network back until the policy of its namespace holds, a cache in a registry or a bucket, a limited network for a task
that reads a provider's secret, and failing a task early whose pod can not start (an image that
can not be pulled, no node for its pool).
