title: "Sources"
description: "The repositories a server may read the code of a run from, the token it reads them with, and the branches a sandbox may push to."
---
`sources` lists the repositories a run with `source: ref` may get its code from, and how
the server reads each. The caller names a repository and a ref, never a URL, and the server
fetches the code itself.

```yaml title="server.yaml"
sources:                            # the repositories a run may get its code from
  - match: github.com/corp/*        # an organisation
    secret: { from: 'gsm:github-readonly-token', account: scm-read }
  - match: gitlab.corp.com/platform/**   # a group with its subgroups
    secret: { from: 'gsm:gitlab-group-token', account: scm-read, username: oauth2 }
```

| Key | What it does |
| --- | --- |
| `match` | The repositories the entry covers, as a pattern of `host/path`. The first entry that matches decides. |
| `secret.from` | The token, as `provider:reference` of a secret provider. Without `secret` the repository is read anonymously. |
| `secret.account` | The [account](/docs/remote-compute/accounts) the token is read as. It needs credentials for that provider. |
| `secret.username` | The user name of the basic authentication the token is sent with, `x-access-token` by default. A GitLab token is commonly sent as `oauth2`. |
| `pushSecret` | The token [sandboxes push](/docs/remote-compute/sandboxes#pushing) with, with `from`, `account` and `username` as `secret`, see [Pushing](#pushing). Without it, nothing pushes to these repositories. |

## Which repositories a run may use

A run from a `ref` names a repository and a ref in its request. The repository is written
`host/path`, such as `github.com/corp/payments` or `gitlab.corp.com/platform/team/tool`;
the server builds the address from it (`https://host/path.git`). A leading `https://` and
a trailing `.git` are dropped; credentials, a port or a query are refused with `400`. Two
lists decide whether it may be used, and a run needs both:

1. **The caller's `repos`**, the patterns of their entitlements added up
   ([Entitlements](/docs/remote-compute/entitlements)). A repository outside of them is `403 you may not run
   from <repo>` at submit, before anything is approved or queued. A caller without `repos`
   can not start runs from a ref.
2. **The server's `sources`**, the repositories it can read at all. `match` is a pattern
   (`github.com/corp/payments` exactly, `github.com/corp/*` for one level,
   `gitlab.corp.com/platform/**` for a group with its subgroups, which covers GitLab
   subgroups) and the first source that matches decides. A repository none covers is
   `400 this server can not read <repo>`.

Both lists use the same patterns, host names and paths are compared in lower case.

## The credential

The credential is a secret of a secret provider, read as a service account of the
operator, like the secrets of a task: `secret.from` is `provider:reference`, `account` is
the account it is read as, and `username` (default `x-access-token`) is the user name of
the basic authentication the token is sent with. A provider command can mint a
short-lived token, for example of a GitHub App; it is read again after a minute. A source
without a `secret` is read anonymously. The token goes to git for that one fetch through
the environment of the git process, scoped to the host of the repository, so it is never
an argument, never written to `.git/config` or the checkout, never in the environment of a
task, and masked in the logs of the run. The account that reads repositories is the
server's own: no entitlement may name it and no build file may use it for a secret.

## Pinning

The server resolves the ref when the run is submitted, with `git ls-remote`:
`refs/heads/<ref>`, else `refs/tags/<ref>` (an annotated tag to its commit). A name that is
both a branch and a tag, or neither, is `400`, a repository it can not reach is `502`. The
run stores the repository, the ref and the `commit`, and the approver sees them. The
executor fetches the ref and fails the run if it no longer points to that commit, so a
branch that moved after the approval does not run other code than the one approved. A
40-digit commit hash is taken as it is; an account with `refs` refuses one, because it
names no branch.

## Pushing

`pushSecret` is the token the server pushes the changes of
[sandboxes](/docs/remote-compute/sandboxes#pushing) with, to the repositories the entry
covers. Who may push to which branches is not the source's to say: the `sandboxes` of an
[entitlement](/docs/remote-compute/entitlements) give a branch pattern the type `push`.

```yaml title="server.yaml"
sources:
  - match: github.com/corp/*
    secret: { from: 'gsm:github-readonly-token', account: scm-read }
    pushSecret: { from: 'gsm:github-agent-push', account: scm-push }
entitlements:
  - subject: { iss: https://idp.corp, sub: 4f1c... }
    sandboxes:
      - repo: github.com/corp/payments
        branches:
          main: pull
          'agent/**': push          # agent/fix-login, agent/team/x; not main
```

A branch pattern is written like an account's `refs`: a name (`agent/fix`), `*` for a part
of one level (`agent/*`) and `**` as the last level for everything below (`agent/**`). Keep
the `push` patterns to branches that nobody else writes to and that no deployment runs from:
a sandbox holds changes nobody reviewed, the push is how they get to a review.

The write token is its own secret, read as its own account, so a server that only reads
never holds a token that writes. Like the read token it goes to one git process through its
environment, is masked, and the account is the server's own: no entitlement may name it and
no build file may use it. That git process gets nothing else to sign in with: no global or
system git configuration, no credential helper, no `.netrc` of a home directory and no ssh
agent, so a push is always the service account's and never the identity of whoever runs the
server. A provider command can mint a short-lived token of a GitHub App
with write access to the repository's contents. A token can not be limited to branches on
the host's side, so protect the branches people work on (`main`, releases) in the
repository as well: a pattern that is too wide is then caught twice.

<Callout type="warn">

**Pushed branches run in your CI.** Most repositories run CI on a push to any branch, with
the repository's secrets: GitHub Actions `on: push`, GitLab pipelines, Buildkite. A branch a
sandbox pushed holds code nobody reviewed, including the build scripts and tests CI runs, and
the workflow files themselves when the token may write them. Before you give a pattern the type `push`:

* keep the push patterns out of CI that holds secrets (`branches-ignore: ['agent/**']`), or
  put the jobs with secrets behind a review (environments with required reviewers, protected
  variables);
* give the token no permission over workflow files (a GitHub App without `workflows: write`),
  so a push that changes them is refused by the host.

</Callout>
