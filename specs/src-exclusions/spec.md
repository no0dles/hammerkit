# Feature Specification: Source Exclusions

**Feature Branch**: `016-src-exclusions`

**Created**: 2026-10-05

**Status**: Draft (planned for 1.8.0)

**Input**: User feedback after the 1.7.0 cache review — `src` can only add files. Folders that mix inputs with docs, vendored code or editor files can't be narrowed without switching to globs, and a glob still makes the whole folder visible to a container task while hashing only part of it.

## Motivation

A task declares its inputs in `src`. Today an entry can only add files: a folder, a file or a glob. To leave something out, a task has to switch to a narrowing glob (`src/**/*.ts`), which has two problems: it gets long as soon as several file types matter, and in a container task it hides nothing — the glob's whole starting folder is mounted, so the task can read files that are not hashed. That is exactly the "visible but unhashed" gap the [caching limitations](../../docs/task/caching.md#limitations-what-the-cache-cant-see) warn about.

A `!` entry that removes paths from a task's sources lets a task say what it doesn't read. Because a wrong exclusion is a false cache hit, the exclusion has to apply to what the task can see as well as to what is hashed.

Since 1.7.0, files generated by a task's dependencies are already left out of its hash automatically, which covers the most common reason to want exclusions (`node_modules`, `dist`, generated code inside a source folder). This feature covers the rest: documentation, vendored folders, fixtures of other tasks and editor files inside source folders.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Exclude part of a source folder (Priority: P1)

A developer declares `src: [src, '!src/**/*.md']`. Editing a markdown file inside `src` keeps the task cached; editing any other file under `src` invalidates it.

**Why this priority**: This is the core value — narrowing a folder without listing every file type that matters.

**Independent Test**: After a run, changing an excluded file is a cache hit and changing a non-excluded file in the same folder is a miss.

**Acceptance Scenarios**:

1. **Given** a task with `src: [src, '!src/docs']`, **When** a file under `src/docs` changes, **Then** the task stays cached.
2. **Given** the same task, **When** a file elsewhere under `src` changes, **Then** the task is a cache miss.
3. **Given** a `!` entry using any glob form `src` supports (`**`, `?`, `[...]`, `{a,b}`, extglobs), **When** files match it, **Then** they are excluded.

### User Story 2 - A container task can't read what it excludes (Priority: P1)

A container task excludes a directory or file. Inside the container, the excluded paths are empty or absent, so a command that reads them fails instead of producing a result the cache can't vouch for.

**Why this priority**: Without it, an exclusion is an unverified promise, and a wrong one is a silent false hit — the defect class 1.7.0 closed.

**Independent Test**: A container task that excludes `src/secret.txt` and runs `cat src/secret.txt` fails; the same task without the exclusion succeeds.

**Acceptance Scenarios**:

1. **Given** a container task excluding a directory, **When** a command lists it, **Then** the directory is empty.
2. **Given** a container task excluding a file, **When** a command reads it, **Then** the read fails or returns nothing.
3. **Given** a local task with an exclusion, **When** it runs, **Then** it can still read the file (local tasks are not sandboxed), and the documentation says so.

### User Story 3 - Feedback on exclusions (Priority: P2)

A developer sees what an exclusion does: `hammerkit ls` shows excluded entries, `explain` never names an excluded file as a cause, and `validate` warns about a `!` entry that excludes nothing.

**Why this priority**: A typo in a `!` entry silently excludes nothing (harmless) or too much (a false hit); visibility makes both noticeable.

**Independent Test**: `validate` on a build file with `!src/nope` (no such path) reports a warning naming the entry.

**Acceptance Scenarios**:

1. **Given** a `!` entry that matches no file, **When** `hammerkit validate` runs, **Then** it warns about that entry.
2. **Given** excluded files, **When** `hammerkit ls` lists the task, **Then** the `!` entries are shown with the sources.

### Edge Cases

- Order of entries MUST NOT matter: a `!` entry removes its matches from every other `src` entry of the same task, and a later positive entry does not re-include them. (Simpler to reason about than `.gitignore` ordering; re-inclusion is not supported.)
- A task whose positive entries are all removed by exclusions has no observable inputs and MUST be treated like a task without `src` (always runs, as do its dependants — SC-001 of the task spec), with the existing "matches no files" warning.
- `!` entries MUST NOT be inherited by dependants as sources; a dependency's exclusions apply to the dependency's own hash and visibility only. (Dependants are keyed by the dependency's task id and state key.)
- Adding, removing or changing a `!` entry MUST change the task id (the declared `src` list already participates).
- An exclusion that covers a dependency's generated output changes nothing: those files are already left out of the hash, and the dependency's outputs stay mounted.
- Kubernetes tasks MUST apply exclusions to what is uploaded into the task's volume.
- A `!` entry with a `$VAR` is substituted like any other `src` entry.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: A `src` entry starting with `!` MUST exclude every path it matches (as a file path or a directory prefix) from the task's state key.
- **FR-002**: Exclusions MUST apply to all positive `src` entries of the task regardless of order; re-inclusion MUST NOT be supported.
- **FR-003**: A container task MUST NOT be able to read excluded paths: excluded directories are masked with an empty volume, excluded files with an empty file, at their path inside the container.
- **FR-004**: The Kubernetes runtime MUST leave excluded paths out of the source upload.
- **FR-005**: `validate` MUST warn about a `!` entry that matches no file; `ls` MUST show exclusions; `explain` MUST NOT report excluded files as causes.
- **FR-006**: A task whose sources are all excluded MUST always run, like a task without `src`.
- **FR-007**: The feature MUST be additive: a build file without `!` entries behaves exactly as in 1.7.0, and `build.schema.json` continues to accept any string in `src` (no schema change).
- **FR-008**: The cache-invariant suite MUST cover exclusions: a change to an excluded file stays a hit, a change to a non-excluded file in the same folder is a miss, and the glob property test includes random `!` entries.

### Key Entities

- **Source exclusion**: a `src` entry prefixed with `!`, a path or glob whose matches are removed from the task's inputs and, for container tasks, from what the task can see.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Changing an excluded file never invalidates the task; changing any other file a positive entry matches always does.
- **SC-002**: A container task that reads an excluded path fails (or reads nothing) instead of succeeding with an unhashed input.
- **SC-003**: A `!` entry that excludes nothing is reported by `validate`.
- **SC-004**: A build file without exclusions produces the same task ids and state keys as 1.7.0.

## Assumptions

- The mount masking (FR-003) uses Docker's ability to mount over a path inside an existing bind mount; masking directories with an anonymous empty volume and files with a read-only empty file is sufficient and needs no copy of the sources.
- Respecting `.gitignore` automatically was considered and rejected: gitignored files are sometimes real inputs (`.env`, local configuration), and silently excluding them would reintroduce false hits.
- Local tasks are not sandboxed; for them an exclusion is the author's promise, documented as such.
