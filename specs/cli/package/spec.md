# Feature Specification: CLI: package

**Feature Branch**: `001-current-state-specs`

**Created**: 2026-05-30

**Status**: Current State (reverse-specified from docs, hammerkit 1.6.0)

**Input**: Existing behavior documented in `docs/cli/package.md`

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Build self-contained Docker images from container services (Priority: P1)

A developer runs `hammerkit package <registry>` to turn every container service in their build file into a Docker image. Each image is named `<registry>/<service>:latest` and contains the service's base image plus the outputs generated by all of its dependency tasks, making the image runnable without hammerkit.

**Why this priority**: This is the core purpose of the command — producing deployable, self-contained images from the build graph.

**Independent Test**: Define a service with one dependency task that generates an output directory. Run `hammerkit package localhost:5000`. Confirm an image named `localhost:5000/<service>:latest` is created and that the generated directory is present inside the image.

**Acceptance Scenarios**:

1. **Given** a build file with a container service that has dependency tasks declaring `generates` outputs, **When** `hammerkit package <registry>` is run, **Then** a Docker image named `<registry>/<service>:latest` is produced with the dependency outputs baked in.

2. **Given** a service with `envs`, `ports`, and `cmd` configured, **When** the image is built, **Then** the image encodes those values (environment variables, `EXPOSE` directives, and the default command) so the service runs correctly without hammerkit.

3. **Given** a service with no dependency tasks, **When** `hammerkit package <registry>` is run, **Then** a valid image is still produced from the service's base image and any mounted sources.

### User Story 2 - Push images to a container registry (Priority: P1)

A CI pipeline operator adds `--push` to upload built images to a remote registry. Registry credentials are supplied via `-u`/`-p` flags. This enables promotion of a tested image across environments without rebuilding.

**Why this priority**: Pushing to a registry is the primary delivery mechanism and is equally critical as building.

**Independent Test**: Run `hammerkit package <registry> --push -u <user> -p <token>` and confirm the image is accessible in the registry under the expected name and tag.

**Acceptance Scenarios**:

1. **Given** `--push` is provided with valid `-u`/`-p` credentials, **When** `hammerkit package <registry> --push -u <u> -p <p>` completes, **Then** the image `<registry>/<service>:<tag>` is available in the remote registry.

2. **Given** `--push` is omitted, **When** `hammerkit package <registry>` completes, **Then** the image is built locally only and not pushed.

### User Story 3 - Pin an explicit image tag for release promotion (Priority: P2)

A release engineer specifies `-t 1.2.3` so the produced image is tagged with a version number or a CI commit SHA rather than `latest`, enabling the same artifact to be promoted across staging and production.

**Why this priority**: Reproducible, version-tagged images are required for safe promotion workflows.

**Independent Test**: Run `hammerkit package <registry> -t 1.2.3` and confirm the resulting image tag is `<registry>/<service>:1.2.3`.

**Acceptance Scenarios**:

1. **Given** `-t 1.2.3` is supplied, **When** `hammerkit package <registry> -t 1.2.3` completes, **Then** the image is tagged `<registry>/<service>:1.2.3` instead of `latest`.

### User Story 4 - Build for a specific target platform (Priority: P2)

A developer on an Apple Silicon machine builds images targeting `linux/amd64` so the images can run on x64 production servers, by passing `--platform linux/amd64`.

**Why this priority**: Cross-architecture builds are a common CI/CD requirement, especially in hybrid development environments.

**Independent Test**: Run `hammerkit package <registry> --platform linux/amd64` on an arm64 host and confirm the produced image manifest declares the `linux/amd64` platform.

**Acceptance Scenarios**:

1. **Given** `--platform linux/amd64` is specified, **When** `hammerkit package <registry> --platform linux/amd64` is run on an arm64 host, **Then** the produced image targets the `linux/amd64` platform.

2. **Given** `--platform` is omitted, **When** `hammerkit package <registry>` is run, **Then** the image targets the host architecture.

### Edge Cases

- Services without a container image (local-only services) are not packaged and are silently skipped.
- Dependency tasks that run locally (without an `image` field) are not supported for packaging.
- The `<registry>` argument is required; omitting it is an error.
- `--push` without `-u`/`-p` relies on pre-authenticated Docker credentials (e.g., `docker login`); no error is thrown by hammerkit for missing flags if the daemon is already authenticated.
- Cross-architecture builds require the Docker daemon to support the requested platform (buildkit/emulation); hammerkit forwards `--platform` to the Docker build and does not validate platform support independently.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST accept a required `<registry>` argument and produce a Docker image named `<registry>/<service>:<tag>` for every container service in the build file.
- **FR-002**: System MUST generate a multi-stage Dockerfile per service that starts FROM the service's base image and copies in the `generates` outputs of all dependency tasks.
- **FR-003**: System MUST apply the service's `envs`, `ports` (as `EXPOSE` directives), and `cmd` to the produced image.
- **FR-004**: System MUST label each produced image with `hammerkit.dev/name` and `hammerkit.dev/id`.
- **FR-005**: System MUST default the image tag to `latest` when `-t`/`--tag` is not specified.
- **FR-006**: When `--push` is supplied, system MUST push the built image to the specified registry; credentials MAY be supplied via `-u`/`--username` and `-p`/`--password`.
- **FR-007**: System MUST default to the host architecture when `--platform` is not specified, and MUST forward the specified platform to the Docker build when `--platform` is provided.
- **FR-008**: System MUST support `-f`/`--filter` and `-e`/`--exclude` label options to limit which services are packaged.

### Key Entities

- **Container service**: A service defined in the build file with a base `image`; the unit of packaging.
- **Registry**: The image-name prefix supplied by the user, used to construct the full image name `<registry>/<service>:<tag>`.
- **Generated output**: Files or directories produced by a dependency task's `generates` field that are baked into the service image.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: After `hammerkit package <registry>`, a runnable Docker image exists locally for each container service, named `<registry>/<service>:<tag>`, containing all dependency task outputs.
- **SC-002**: After `hammerkit package <registry> --push`, the image is accessible from the remote registry under the expected name and tag without any additional build steps.
- **SC-003**: An image built with `hammerkit package <registry> -t <version>` carries exactly the tag `<version>` (not `latest`).
- **SC-004**: An image built without hammerkit present in the runtime environment starts the service correctly using its declared `cmd`.

## Assumptions

- Packaging operates exclusively against the Docker runtime; non-Docker (local) services are out of scope.
- The `--build-override-user` flag creates and runs a dedicated uid/gid 1000 user inside the image; its exact semantics beyond that are not specified in the doc and are not elaborated here.
- The `<registry>` value is a plain string prefix with no validation by hammerkit; any registry format accepted by Docker is valid.
- Services with no `deps` still produce a valid image from their base image and `mounts`; this is documented as supported behavior.
