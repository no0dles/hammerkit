Tasks are the pieces of work needed to build or develop your project.

A minimal task contains just a list of commands.
```yaml
tasks:
  example:
    cmds:
      - echo "minimal example"
```

<Callout type="info">

**Local vs. container — the one rule to remember.** If a task declares an `image`,
its commands run **inside that container**. If it has no `image`, they run
**directly on your host** using the tools installed there. Everything else (sources,
outputs, caching, dependencies) works the same in both cases. Containers are the
recommended default: they remove the need to install build tools on every machine
and make a build behave identically on your laptop and in CI. See
[run a task in a container](/docs/task/container).

</Callout>

## Anatomy of a task
A task is built from a small, fixed set of fields:

| Field | Purpose |
|-------|---------|
| `cmds` | The commands to run, in order. |
| `image` | Run the commands inside this container image. Omit to run on the host. |
| `src` | Input files/folders. Used for [caching](/docs/task/caching) — unchanged sources let the task be skipped. |
| `generates` | Output files/folders the task produces. This is what gets cached, stored and restored. |
| `deps` | Other tasks that must run first (see [dependencies](/docs/task/dependencies)). |
| `needs` | Services that must be running first (see [needs](/docs/task/needs)). |
| `mounts` | Extra paths to make available to a container task (see [container](/docs/task/container)). |
| `envs` | [Environment variables](/docs/build-file/environment-variables) for the commands. |
| `labels` | Group/filter tasks (see [labels](/docs/labels)). |
| `cache` | The [caching](/docs/task/caching) method/backend for this task. |
| `timeout` | Maximum execution time, e.g. `10m` (see [timeouts](#timeouts)). |
| `resources` | CPU and memory limits of the container (see [resources](#resources)). |
| `runner` | The server the task has to run on (see [runner](#runner)). |

## Source files (`src`)
Tasks that depend on input files should declare them under `src`.
Hammerkit detects whether the `src` files have changed compared to previous runs and skips execution if they are unchanged.

```yaml
tasks:
  build:
    description: "run typescript build"
    src:
      - tsconfig.json
      - src
    cmds:
      - tsc
```

## Generated files (`generates`)
Tasks that produce output files should declare them under `generates`.
Hammerkit archives generated files, so build outputs can be cached, stored and restored.

```yaml
tasks:
  build:
    description: "run typescript build"
    src:
      - tsconfig.json
      - src
    generates:
      - dist
    cmds:
      - tsc
```

### Exporting generated files
By default generated files of a container task stay inside the container volume.
Mark a generate with `export: true` to copy it back into your workspace after the
task ran. This is useful when another tool outside hammerkit needs the produced
files, for example a build artifact you want to inspect or publish.

```yaml
tasks:
  build:
    image: node:alpine
    generates:
      - path: dist
        export: true
    cmds:
      - tsc -b
```

An exported output is copied back only when the task succeeds. Test reports,
screenshots and videos are most useful when a test fails: mark those
`export: always` and hammerkit copies them to the workspace even when the task
exits non-zero. A failed task is never cached, so nothing else changes.

```yaml
tasks:
  e2e:
    image: cypress/included:13.15.0
    generates:
      - path: cypress/videos
        export: always
    cmds:
      - cypress run
```

### Outputs start empty
When a task runs, its outputs start empty: hammerkit deletes what an earlier run
left in them before the task's commands run. A file a deleted source used to
produce, or a partial result of a failed run, would otherwise end up in the next
result and in the cache.

An output that is also a source of the task, or contains one, is left alone: a
`package-lock.json` that `npm install` both reads and writes keeps its content.

Set `resetOnChange: false` on an output to keep its content between runs, for a
tool that builds incrementally on top of its previous output:

```yaml
tasks:
  build:
    image: rust:1.90-slim
    src: [Cargo.toml, Cargo.lock, src]
    generates:
      - path: target
        resetOnChange: false   # cargo reuses what it compiled before
    cmds:
      - cargo build --release
```

Whatever such an output keeps becomes part of the next result, so prefer a
[mount](/docs/task/container#adding-mounts) for a tool's cache: a mount is never
part of a task's result.

## Timeouts
A task that hangs — a deadlocked test, a stuck network call — would otherwise block
the run until your CI provider kills the job. Set a `timeout` and hammerkit aborts
the task once it runs longer, fails it with `timed out after <duration>`, and stops
the run like any other failure.

```yaml
tasks:
  e2e:
    image: cypress/included:13.15.0
    timeout: 15m
    cmds:
      - cypress run
```

Durations are written as a number plus a unit: `ms`, `s`, `m`, `h` or `d`, and can
be combined (`1h30m`). A timed-out task is cleaned up the same way as a cancelled
one — its container or Kubernetes job is removed — and never writes a cache entry.
The timeout does not affect the task's cache key.

To give every task a default, pass `--timeout` to [`run`](/docs/cli/execute) or
[`up`](/docs/cli/up); a task's own `timeout` takes precedence.

```bash
hammerkit run --timeout 30m
```

## Resources
A heavy build step can take every core and all the memory of the machine it runs
on. Declare `resources` and hammerkit limits the task's container to them, and
plans the run by them.

```yaml
tasks:
  build:
    image: node:22
    resources:
      cpus: 2
      memory: 4Gi
    cmds:
      - npm run build
```

Both fields are optional and use Kubernetes notation: `cpus` as cores (`2`, `0.5`)
or millicores (`500m`), `memory` with a `Ki`/`Mi`/`Gi`/`Ti` suffix (at least `6Mi`).
`cpus` and `memory` set the limit and request the same. To set them apart, use
`requests` and `limits`; a request must not exceed its limit, and a request without a
limit is not capped:

```yaml
tasks:
  build:
    image: node:22
    resources:
      requests: { cpus: 500m, memory: 1Gi }
      limits: { cpus: 2, memory: 4Gi }
    cmds:
      - npm run build
```

On Docker the limits become the container's CPU and memory limits, and a memory
request below its limit a soft memory reservation. On Kubernetes the job container
gets the same `requests` and `limits`. A task that exceeds its memory limit is killed
by the runtime and fails. `cpus` above what the Docker host has runs the container
without a CPU limit, with a warning, as such a limit would limit nothing. On
Kubernetes a request beyond what any node offers leaves the pod Pending.

A local task can declare `resources` too, but nothing limits it;
[`validate`](/docs/cli/validate) and `run --dry-run` say so. Resources are not part
of the task's cache key: changing them does not rebuild the task.

### Planning the run
The requests also plan the run on the machine hammerkit runs on, for local tasks and
for containers on Docker (on Kubernetes the cluster places pods by their requests):

* **Before anything starts**, hammerkit checks that every task fits, together with the
  services it needs. A task whose requests plus those of its services exceed the
  host's CPUs or memory fails the run up front, naming the task, instead of hanging or
  being killed halfway. With `up`, all services must fit together.
  `--skip-resource-check` starts anyway.
* **While it runs**, a task starts only when its requests fit next to everything
  running, the services included. When every task and service on the host requests
  both `cpus` and `memory`, the run is not capped at a worker count (`--concurrency`,
  default 4): as many tasks run in parallel as the requests allow. Otherwise
  `--concurrency` still caps the run, and tasks with requests also wait for room. A
  task that alone exceeds the host runs once nothing else does.

The capacity is the Docker host's when containers run there, else this machine's.
`HAMMERKIT_CPUS` and `HAMMERKIT_MEMORY` (e.g. `8`, `16Gi`) set it, for a CI runner
that shares its machine, for example.

## Runner

<Callout type="warn">

Experimental. A task can name its server already, but running on one arrives in a
follow-up release. Until then a run that resolves to a server stops with an error
instead of running locally.

</Callout>

`runner` names a server registered with [`hammerkit remote add`](/docs/cli/remote),
for a task that has to run somewhere else, such as a Mac mini for an Xcode build.
Set it on a task or as a default for the whole build file; `extend` inherits it.

```yaml
runner: linux-pool # default of the tasks of this file

tasks:
  ios:
    runner: mac-mini
    cmds:
      - xcodebuild -scheme app
```

The build file holds a name only. The URL and the OAuth issuer live in the host
config, so a project can't send your source code to a server you never registered.

Where a run happens, highest first:

1. `--on` / `--local` (follow-up release)
2. the `HAMMERKIT_ON` environment variable (`local`, `auto` or a server name)
3. the `runner` of the tasks in the run
4. `run.on` of the host config, set with `hammerkit remote use`
5. the local machine

`auto` stands for the tasks' `runner`, else local. A run goes to a single server, so
tasks that name different servers fail the run, and a name that is not registered
is an error: hammerkit never quietly runs a task somewhere else than you asked.
`local` and `auto` can't be used as a `runner`.
