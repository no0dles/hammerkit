<Callout type="warn">

Experimental. The server checks OAuth tokens, keeps published build files and runs
their tasks for callers who are entitled to. The config and the API can still change
between releases, see the
[remote compute spec](https://github.com/no0dles/hammerkit/blob/master/specs/remote-compute/spec.md).

</Callout>

`server` turns a machine into the target of remote runs: a Mac mini for iOS builds,
a Linux box with big CPUs, later a Kubernetes cluster. It reads its own config
file, so it needs no build file.

```bash
hammerkit server --config /etc/hammerkit/server.yaml
```

The server runs until it is interrupted. `HAMMERKIT_SERVER_CONFIG` can stand in for
`--config`.

## Config

The file belongs to whoever operates the server and is reviewed like code. Unknown
keys are an error, so a typo is not silently ignored.

```yaml
listen:
  host: 127.0.0.1   # default
  port: 8480        # default
tls:
  cert: /etc/hammerkit/tls.crt
  key: /etc/hammerkit/tls.key
issuers:
  - issuer: https://login.example.com
    audience: hammerkit
    groupsClaim: groups   # default
    clientId: hammerkit-cli
    scope: openid api://hammerkit/.default
secretProviders:                    # the commands that read secrets, see Secret providers
  gsm:
    command: [gcloud, secrets, versions, access, latest, '--secret={{ref}}']
accounts:                           # the service accounts a secret can be read as
  op-payments-dev:
    description: Payments, test secrets
    providers: { gsm: { env: { CLOUDSDK_AUTH_CREDENTIAL_FILE_OVERRIDE: /etc/hammerkit/creds/payments-dev.json } } }
  op-payments-prod:
    description: Payments, production
    providers: { gsm: { env: { CLOUDSDK_AUTH_CREDENTIAL_FILE_OVERRIDE: /etc/hammerkit/creds/payments-prod.json } } }
    source: [ref]                   # only from reviewed code
    refs: [main, 'release/*']       # and only from these branches
  scm-read:                         # reads the repositories, no entitlement may name it
    description: Read-only access to source repositories
    providers: { gsm: { env: { CLOUDSDK_AUTH_CREDENTIAL_FILE_OVERRIDE: /etc/hammerkit/creds/scm-read.json } } }
entitlements:
  - subject: { iss: https://login.example.com, sub: 4f1c2b }
    accounts: { op-payments-dev: use, op-payments-prod: request }
    builds: run
  - group: { iss: https://login.example.com, name: release-managers }
    accounts: { op-payments-prod: use }
    builds: publish
  - claims:
      iss: https://token.actions.githubusercontent.com
      match: { repository: corp/payments, ref: refs/heads/main }
    accounts: { op-payments-dev: use }
    repos: [github.com/corp/payments]
    builds: publish
sources:                            # the repositories a run may get its code from
  - match: github.com/corp/*        # an organisation
    secret: { from: 'gsm:github-readonly-token', account: scm-read }
  - match: gitlab.corp.com/platform/**   # a group with its subgroups
    secret: { from: 'gsm:gitlab-group-token', account: scm-read, username: oauth2 }
runtimes: [docker]   # what tasks may run on, docker by default
approvals:
  timeout: 1h        # default
  maxWaiting: 100    # default
  cooldown: 10m      # default, a rejected version can not be proposed again before
storage:
  directory: /var/lib/hammerkit   # default ~/.hammerkit/server
runs:
  maxConcurrent: 4   # default
  keep: 200          # default
  limits:            # per caller (issuer and subject), 429 over it
    waiting: 10      # default, runs that wait for an approval
    queued: 20       # default, runs that wait for a free place
    running: 2       # default, runs that execute at once, the others wait in the queue
  maxDuration: 1h    # default, a longer run is stopped and fails
  maxLogBytes: 1048576   # default, log output kept per run
  env:
    allow: [PATH, HOME, DOCKER_HOST]   # the only variables of the server a run sees, none by default
    set: { CI: 'true' }
backend:
  type: host
  platform: { os: macos, arch: arm64 }   # detected when left out
```

| Key | What it does |
| --- | --- |
| `listen` | Interface and port. Port `0` picks a free one. |
| `tls` | Certificate and key to serve https. |
| `behindTlsProxy` | Set to `true` when a proxy in front terminates TLS. |
| `issuers` | The OAuth issuers whose tokens are accepted, with the audience they must carry and the claim that lists a caller's groups. At least one: OAuth is the only way to call the server. The issuer is an https URL (http for localhost). `clientId` and `scope` are what [`remote login`](/docs/cli/remote#signing-in) signs in with; an issuer without a `clientId` only takes tokens obtained elsewhere. |
| `secretProviders` | The commands that read secrets, the same as the `secretProviders` of a build file, see [Secret providers](/docs/task/secret-providers). A published build file can not declare them, only the operator does. |
| `accounts` | The service accounts a secret can be read as, each with the environment that makes the provider command act as that account, see [below](#accounts). |
| `entitlements` | Who may use or request which service account, and what they may do with build files, see [below](#entitlements). |
| `approvals` | How long a requested run waits for its approval (`timeout`), how many may wait (`maxWaiting`) and how long a rejected proposal has to be waited out (`cooldown`), see [Approvals](#approvals) and [Proposing a version](#proposing-a-version). |
| `sources` | The repositories a run with `source: ref` may get its code from, see [Repositories](#repositories). |
| `runtimes` | What tasks may run on: `docker` (containers, the default) and `local` (commands on this machine as the user of the server, which have to be allowed by name). A build file with a task on a runtime that is not listed is refused when it is published or proposed, see [What a build file may not do](#what-a-build-file-may-not-do). The server logs a warning at startup when `local` is allowed. |
| `storage` | Where the server keeps what must survive a restart: the published build files and the records of the runs (`records/`). Runs work in `runs/` below it while they run. |
| `runs` | `maxConcurrent` runs execute at the same time, the others wait in queue. `keep` finished runs are remembered, the oldest are dropped first. `limits` is what one caller may have at a time, see [Limits and restarts](#limits-and-restarts). `maxDuration` stops a run that executes longer, and `maxLogBytes` cuts off the log of a run that says more. `env.allow` lists the variables of the server process that a run, its provider commands and the git fetch can see, and `env.set` adds fixed values; nothing else of the server's environment is passed on, and the list is empty by default. A server that runs tasks needs `PATH` in it, Windows needs its system variables (`SystemRoot`, `ComSpec`, `PATHEXT`, `TEMP`) as well. |
| `backend` | Where tasks run. `host` is this machine, with the docker and local runtimes. `platform` is what the machine offers: `os` is `linux`, `macos` or `windows`, `arch` is `amd64` or `arm64`. |

Plain http carries OAuth tokens, so it is accepted on the loopback interface only.
Anywhere else the config needs `tls`, or `behindTlsProxy: true`.

## Authentication

Every call except discovery and the health check carries an OAuth access token as
`Authorization: Bearer <token>`. The server fetches the issuer's keys from its
OpenID discovery document and accepts a token only when

* it is signed with `RS256`, `RS384`, `RS512`, `PS256`, `ES256`, `ES384` or `ES512`
  (never `none` or a shared secret),
* its `iss` is one of the configured issuers and its `aud` contains the configured
  audience,
* it has not expired and is already valid (a minute of clock skew is allowed), and
* it has a `sub`.

Keys are cached for ten minutes, and fetched again, at most once a minute, when a
token names a key the server does not know yet, so a rotation needs no restart. A
refused token only gets `401 invalid token`; the reason goes to the server's log,
with everything a caller sent quoted and stripped of control characters, so a caller
can't forge log lines. Concurrent requests share one key fetch, a failing issuer is
left alone for ten seconds, and the previous keys keep working for up to an hour
while the issuer is down.

Two things the server does not check, so set them up on the identity provider:

* `aud` has to be an API audience for the server, not the OAuth client's own id, or an
  ID token for that client would be accepted. The server does not look at the token
  type (`typ`) or the authorized party (`azp`).
* A `claims` entitlement matches any string claim as it finds it. It does not know
  that `email` needs `email_verified`; match on `sub`, a group or a claim the
  provider controls.

### Accounts

A service account is a name the operator defines. The secrets in a published build
file say which account each is read as (`account:` on the secret), and the server
derives from that which accounts a run uses: a task without secrets uses none and holds
no credentials. Nothing in a run request, no default and no `account` on a task or
service chooses one, so the person who asks for a run cannot pick the account they
prefer.

```yaml
tasks:
  test:
    cmds: [npm test]            # no secrets, no account
  deploy:
    secrets:
      - from: gsm:kube-token
        account: op-payments-prod
        env: KUBE_TOKEN
    cmds: [./deploy.sh]
```

An account has a `description`, the `providers` environment that makes each secret
provider command act as the account (the credentials are files and variables of the
operator's machine, they never reach the config), and optionally

* `source`: where the code of a run using the account may come from, `upload` for
  the caller's working tree and `ref` for a git ref. Both when left out.
* `refs`: the branches or tags (`release/*` matches one level) such a run may start
  from. It needs `source: [ref]`, and a bare commit is refused because it names no
  branch.

Because the account is chosen by the published file, a server applies stricter rules
to secrets than a local run does: a provider secret names its account (`account:`
is required, a task's `account:` and `default: true` are not used), `file:` secrets
are refused, and an `env:` secret may only read a variable listed in `runs.env.allow`.
A build file that declares `secretProviders` or `secretAccounts` is refused, and so is
a project `.env` file read: the operator's providers and accounts are the only ones.

### Entitlements

An entitlement says which service accounts a caller may use, and what they may do
with build files. The server matches the validated claims of the token only, never
anything the caller sends along.

| Who | Matches |
| --- | --- |
| `subject: {iss, sub}` | exactly that person or client |
| `group: {iss, name}` | every caller of that issuer whose groups claim lists the name |
| `claims: {iss, match}` | every token of that issuer whose string claims equal all of `match`, for CI jobs (repository, ref, environment) |

A caller gets what all entitlements that match give, and nothing when no entry
matches. Every account that an entitlement names has to be defined under `accounts`,
a typo stops the server at startup.

`accounts` maps an account to a level:

* `use` runs on the account at once and approves the runs others request on it.
* `request` lets the caller ask for runs on the account. Such a run waits until
  somebody who may `use` the account approves it, see [Approvals](#approvals).

When several entitlements give a level for the same account, `use` wins. `builds` is
what the caller may do with [build files](#build-files), one level that includes the
lower ones:

| `builds` | May |
| --- | --- |
| `run` | start runs of published build files. Without a level nothing runs, an account alone does not allow it. |
| `propose` | also send new versions, which somebody who may publish approves, see [Proposing a version](#proposing-a-version). |
| `publish` | also publish new versions of any build file. Who defines the work does not have to be who runs it. |

Build files are named by whoever publishes them, so the config never lists names.
`repos` lists the repositories (`github.com/corp/payments`, `github.com/corp/*` for
one level, `gitlab.corp.com/platform/**` for a group with its subgroups) the caller
may name in a run from a git ref; the union of the matching entitlements applies.
Every grant is written to the log with issuer, subject, accounts and the entitlements
that matched. A caller with no account and no `builds` level can do nothing on the
server, they are not even shown which build files exist.

`GET /v1/me` returns the identity and what the caller may use, and `GET /v1/accounts`
the accounts they have a level on, with their description and the sources they allow:

```json
{
  "iss": "https://login.example.com",
  "sub": "4f1c2b",
  "accounts": [
    { "name": "op-payments-dev", "level": "use" },
    { "name": "op-payments-prod", "level": "request" }
  ],
  "repos": ["github.com/corp/payments"],
  "builds": "run"
}
```

## Build files

A run does not bring its own build file. The server keeps the build files that
were published to it, and a run says which one to use and which of its tasks to
execute. So whoever may run work cannot change what a task does, and what a task
does is decided by whoever may publish.

```
PUT /v1/definitions/payments
```

```json
{
  "entry": ".hammerkit.yaml",
  "files": {
    ".hammerkit.yaml": "tasks:\n  build:\n    cmds: [npm run build]\n",
    "web/.hammerkit.yaml": "..."
  }
}
```

A published build file is a bundle: the file that starts it (`entry`, the usual
`.hammerkit.yaml` when left out) and every file it includes, as text, up to 200
files and 1 MiB. The name says what it is for (letters, digits, `.`, `_` and `-`).
The server reads the bundle the way a run would, in a directory of its own where
only the bundle's files exist, so one that does not load is refused when it is
published and not when somebody wants to run it (`400`). A bundle may not include
anything outside of itself. Includes from git have to be pinned to a commit and
come from an `https://` or `ssh://` address, because the version below can only
vouch for what is in the bundle.

**Versions.** Every bundle has a version, the hash of its files:
`sha256:<hex>` of the JSON `[entry, [[path, sha-256 of the content], ...]]` with
the paths sorted. The same files have the same version anywhere, so a client can
compute it and compare it with the server's. A version is never changed; publishing
different files under the same name adds a version, publishing the same files again
answers `200` and changes nothing (the first publish answers `201`).

| Call | What it does |
| --- | --- |
| `PUT /v1/definitions/<name>` | Publish a bundle. Needs `builds: publish`, else `403`. With `builds: propose`, or when the bundle names accounts the caller does not `use`, it is a [proposal](#proposing-a-version) and answers `202`. |
| `GET /v1/definitions` | The names with their latest version. |
| `GET /v1/definitions/<name>` | The versions of one, newest first, with who published each, the tasks and services it has and what each task works on (`inputs`). |
| `GET /v1/definitions/<name>/<hash>` | One version. `latest` stands for the one published last. |
| `GET /v1/definitions/<name>/<hash>/files` | The files of one version, to see what would run. |
| `POST /v1/definitions/<name>/<hash>/yank` | Pull a version back, see [Yanking](#yanking-a-version). The body is optional: `{ "reason": "..." }`. |
| `POST /v1/definitions/<name>/<hash>/unyank` | Let a yanked version go on. Needs `builds: publish`. |

Reading needs a token and at least one service account or `builds` level. Versions are kept in the `storage` directory and survive a restart.

**Inputs.** A version lists, for every task, what it works on, so a client knows
which of its files a run needs without planning the build file itself:

```json
"inputs": {
  "build": { "src": ["package.json", "src/**/*.ts", "!src/**/*.spec.ts"], "mounts": [], "deps": [], "needs": [] },
  "test": { "src": [], "mounts": [".npm"], "deps": ["build"], "needs": ["db"] }
}
```

`src` are the patterns of the task's own `src` as the build file writes them
(environment variables are not substituted), `mounts` are the host paths a
container task mounts, `deps` the tasks and `needs` the services it waits for. Paths
are relative to the root of the bundle, which is also the root of the project's
files, and a path outside of it is left out because it cannot be sent. What a task
inherits from its dependencies is listed with those. Versions published before this
was recorded have no `inputs`.

**Plan and accounts.** A version also carries a `plan`, what each task and service
does as the engine reads it, and the `accounts` its secrets are read as. A reviewer
or an agent sees `deploy` uses `op-payments-prod` before anything runs:

```json
"accounts": ["op-payments-prod"],
"plan": {
  "deploy": {
    "kind": "task", "runtime": "docker", "image": "node:22",
    "cmds": ["./deploy.sh"], "deps": [], "needs": [],
    "accounts": ["op-payments-prod"],
    "secrets": [{ "from": "gsm:kube-token", "account": "op-payments-prod", "target": "KUBE_TOKEN" }],
    "mounts": [], "ports": [], "generates": [],
    "flags": ["local-task"]
  }
}
```

The plan never holds a value of a secret, only where it is read from. `flags` are what a
reviewer looks at first: `local-task` (it runs on the host, not in a container),
`host-port` (it binds a port of the host) and `remote-include` (it includes a file from
git). A bundle that names an account the server does not define is refused and the
message lists the accounts that exist.

**Publishing and accounts.** A bundle that uses an account the publisher does not
`use` becomes a [proposal](#proposing-a-version) even for `builds: publish`, and is
approved by somebody who may publish and who uses the accounts the proposer lacks. So
one person can not publish a task that reads the production key for somebody else to
run without a second pair of eyes.

**What a build file may not do.** A build file is written by whoever publishes it and runs
with what the operator gave the server, so a bundle is refused (`400`, naming the file and
task) when it

* names `environments`: the docker host or Kubernetes cluster is the server's to choose,
* has a service for Kubernetes (`selector`, `kubeconfig` or `context`),
* names a cache backend other than the server's own (`s3`, `registry`, or a `path`),
* mounts a path outside of the bundle into a container, such as the docker socket, `/etc`
  or a home directory,
* has a task on a runtime that `runtimes` does not allow,
* declares `secretProviders` or `secretAccounts`, reads a `file:` secret, reads an `env:`
  secret the server does not list in `runs.env.allow`, or reads a secret as the account
  that reads repositories (see [Accounts](#accounts) and [Repositories](#repositories)).

Without this a task with no secrets would still reach what the operator's machine can: a
published file would be enough to send a run, or the cache, to a host of its choosing.

### Proposing a version

Who defines the work decides what runs, so a new version of a build file can wait for
a second pair of eyes. `builds: propose` is the lower level of `publish`, like
`request` is the lower level of `use`:

```yaml
entitlements:
  - group: { iss: https://login.example.com, name: platform }
    accounts: { op-payments-prod: use }
    builds: publish
  - claims:
      iss: https://login.example.com
      match: { client: coding-agent }
    builds: propose
```

A caller who may only propose sends the same `PUT`. The server reads the bundle as it
does for a publish and refuses one that does not load, then keeps it as a
**proposal** (`202`). A publish also ends up here when the bundle names accounts the
publisher does not `use` (`missing` lists them). It is not a version: it can not be
run, `latest` does not change and the build files are not listed with it. Someone who
may `publish`, uses the accounts in `missing`, and did not propose it, approves it,
and only then it is published, as the proposer's version with the approver recorded as
`approvedBy`. That is the version runs refer to by hash, so what was approved is what
runs.

| Call | What it does |
| --- | --- |
| `GET /v1/proposals` | The proposals the caller made or may see, newest first, with `state` (`waiting`, `approved`, `rejected`, `expired`), who proposed it, the tasks and services, the `accounts` and the `missing` ones, `plan`, `base` (the latest version when it was proposed, the one it follows), `latest`, `stale` and whether the caller `canDecide`. |
| `GET /v1/proposals/<name>/<hash>` | One of them. |
| `GET /v1/proposals/<name>/<hash>/files` | Its files, to read what would be published. |
| `POST /v1/proposals/<name>/<hash>/approve` | Publish it. The body is optional: `{ "reason": "..." }`. |
| `POST /v1/proposals/<name>/<hash>/reject` | Drop it; the reason (up to 500 characters) is kept with it. |

A proposal is visible to its proposer and to everyone who may publish; what the caller
neither proposed nor may decide does not exist for them (`404`), and one that is
decided or expired is `409`. A proposal expires after the `approvals.timeout` like a
requested run does, and `approvals.maxWaiting` limits the proposals that wait (`503`).
Proposals are kept in memory, unlike runs: after a restart the proposer proposes again. Each
proposal and decision is logged with who made it.

**Only while it follows the latest.** A proposal records the latest version when it is
made (`base`). If another version of the build file is published before it is decided, it
is `stale`: it can only be rejected, approving answers `409`, because publishing it would
put an old file in front of newer work for everyone who runs `latest`. The proposer
proposes again on top of the new version.

**No git includes.** A proposal is read before anybody approved it. A bundle that
includes from git would make the server fetch from the network for a caller who may
only propose, so a proposal with `includes` or `references` from git is refused
(`400`). Whoever may publish can use them.

**Cooldown.** After a rejection, the proposer can not propose that build file again,
and nobody that version, for `approvals.cooldown` (default `10m`): `429`, with the time
left. A proposal that only ran out of time does not start one. It keeps the people who
decide from being asked again and again; like the proposals it is forgotten by a restart.

A proposal approves a new version of the build file, not the code its commands run:
`npm test` still executes the files a run brings. Production accounts stay behind
[`request`](#approvals) and `source: [ref]`.

### Yanking a version

A published version is never changed, but one can be pulled back when it should not run
any more (it leaks a token, it deploys to the wrong place). `POST
/v1/definitions/<name>/<hash>/yank` is open to whoever has `builds: publish`, and to
whoever `use`s an account the version works with: the people who answer for what runs
as that account do not have to wait for a publisher. The body may carry a `reason`, up
to 500 characters.

A yanked version is not `latest` any more, a run that names it is refused with `409`
and the reason, and a run that was accepted before, and still waits for an approval or in
the queue, fails when it would start. Runs that already execute are not stopped; cancel
them. The version and its files stay on the server for the record, and the version lists
show who yanked it and why. `unyank` lets it go on, and needs `builds: publish`. Both are
logged with who did it, and a yank survives a restart.

## Source files

A run from an `upload` works on the caller's files. They are sent in two steps so
that only what the server does not have yet travels: the caller announces the tree
as a list of files with their digests, the server says which digests it lacks, and
the caller sends those.

```
POST /v1/sources
```

```json
{
  "files": [
    { "path": "package.json", "sha256": "9f2c...", "size": 812 },
    { "path": "bin/run.sh", "sha256": "41ab...", "size": 233, "mode": "exec" }
  ]
}
```

The answer names the tree, a **snapshot**, and says what is missing:

```json
{
  "snapshot": "sha256:5d1e...",
  "files": 2,
  "bytes": 1045,
  "createdAt": "2026-10-11T11:00:00.000Z",
  "missing": ["9f2c...", "41ab..."],
  "complete": false
}
```

The snapshot is the `sha256:<hex>` of the JSON `[[path, sha-256, mode], ...]` with
the paths sorted, the same construction as the version of a build file, so the same
files have the same name anywhere. It answers `201` for a new tree and `200` for
one the server already knows. Then each missing file is sent on its own:

| Call | What it does |
| --- | --- |
| `POST /v1/sources` | Announce a tree. Up to 20,000 files, 32 MiB per file, 1 GiB per tree. |
| `PUT /v1/sources/blobs/<sha256>` | Send the content of one file as the request body. Answers `201`, or `200` when the server had it. |
| `GET /v1/sources` | The trees the caller keeps, what they take and the limit. |
| `GET /v1/sources/<snapshot>` | One tree and the digests still missing; `complete` when none is. |
| `DELETE /v1/sources/<snapshot>` | Forget a tree and the content no other tree of the caller needs. |

A second run after one edited file announces the tree again and sends that file
only. A client can also skip the announcement when the snapshot it computes is the
one it used last and `GET /v1/sources/<snapshot>` says it is complete.

* **Only the caller's.** Trees and content belong to the caller who sent them;
  another caller's snapshot is `404`. Content is never shared between callers: a
  server that answers "I already have this file" to anybody would tell them what
  other people work on.
* **Only announced content.** A file is taken only if a tree the caller announced
  lists its digest, with the size announced, and only if the content has that
  digest. Anything else is `400`.
* **Credentials do not leave.** A tree with a path that looks like a credential is
  refused with `400` that names it, even when a `src` pattern reaches it: `.env`
  (not `.env.example`, `.env.sample`, `.env.template`), `.npmrc`, `.netrc`,
  `.pypirc`, `.git-credentials`, private keys (`id_rsa` and its kin, `*.pem`,
  `*.p12`, `*.pfx`) and anything below `.git/`, `.ssh/`, `.aws/`, `.gnupg/` or
  `.kube/`. Secrets belong in a secret provider; there is no override.
* **Quota.** A caller may keep 4 GiB; a file that would go over is `413`. Nothing
  is removed on its own, a caller deletes what they no longer need.
* **Who may.** Callers with a `builds` level; others get `403`. An account can
  further restrict its `source`.

Paths are relative to the root of the project, forward slashes, nothing that climbs
out; `inputs` of a [build file version](#build-files) say which files a run needs.

## Runs

A run is a request to execute tasks of a published [build file](#build-files). The server writes every run
down in `storage` (`records/`, readable by the user of the server only), so a restart keeps them with their
logs, see [Limits and restarts](#limits-and-restarts). Every call needs a token, and a run can be
seen and cancelled only by the caller that submitted it: for anyone else its id is
`404`, the same as an id that does not exist.

| Call | What it does |
| --- | --- |
| `POST /v1/runs` | Submit a run. Answers `202` with the run in state `queued`, or `awaiting-approval` when the caller only has the account on [`request`](#approvals). |
| `GET /v1/runs` | The caller's runs, newest first. |
| `GET /v1/runs/<id>` | One run: `state` is `awaiting-approval`, `queued`, `running`, `succeeded`, `failed`, `cancelled` or `rejected`; a failed or rejected run has an `error`. |
| `POST /v1/runs/<id>/cancel` | Cancel a run: one that is queued or waits for an approval at once, a running one when its tasks have stopped. |
| `GET /v1/runs/<id>/events` | The run's events as server-sent events, see below. |

```json
{
  "definition": { "name": "payments", "hash": "sha256:9f2c..." },
  "tasks": ["build", "test"],
  "source": { "type": "ref", "ref": "refs/heads/main" },
  "options": { "env": "staging", "cache": "checksum", "timeout": "30m" }
}
```

* `definition` names the published build file and the version to run: a hash, or
  `latest` when left out. The run is pinned to the version the server chose, which
  the answer shows, so what it executes does not change under it. A name or version
  that does not exist is `400`.
* `tasks` are task names as on the command line, up to 100. A task the build file
  does not have is `400`. Instead of names, labels in `options.filter` can select
  the tasks.
* There is no account in the request. The run uses the accounts of the secrets of the
  tasks it executes, with their dependencies and the services they need, derived from
  the pinned version, and the answer lists them as `accounts`. A caller who has no
  level on one of them gets `403` naming the account, one who may only `request` it
  gets a run in `awaiting-approval`, and a caller without `builds` level may not run.
* `source` says where the code comes from: `{ "type": "ref", "repo": "github.com/corp/payments", "ref": "main" }`
  for a branch or tag of a repository (or a full commit hash) that the server checks out itself, or `{ "type": "upload", "snapshot": "sha256:..." }`
  for the caller's working tree, announced and sent beforehand, see [Source
  files](#source-files). A snapshot that is unknown, or that still lacks files, is
  `400`. The kinds the accounts of the run list in `source` (and, for `refs`, the
  branches) are the only ones allowed, anything else is `403`.
* `options` are the settings of `hammerkit run` that make sense on a server, all
  optional: `env`, `filter` and `exclude` (labels), `cache` (`checksum`, `modify-date` or `none`),
  `cacheReadOnly`, `timeout` (for example `30m`) and `skipDeps`. How many tasks run in
  parallel and how much of the machine they use stay with the server, and `watch` and
  the log mode are for terminals only, so they are not accepted.

The request names the work, it does not contain it: what the tasks do comes from the
published build file, and the files they work on come from `source`. A `ref` is
fetched by the server. An `upload` refers to a snapshot of the working tree that is
sent separately, so the request stays small however large the project is.

The body is JSON up to 64 KiB, and unknown fields are rejected. Each submitted run is
logged with who submitted it, the accounts and the source.

The events carry the sequence number as their `id`, so a client that lost the
connection continues with the `Last-Event-ID` header (or `?after=<n>`) and misses
nothing. The stream replays what happened and then follows the run until it is over;
a finished run's events are replayed and the stream ends. Event types are `state`
(`awaiting-approval`, `queued`, `running` and the final state, with the `error` of a failed run), `approval`
(who approved or rejected the run), `task` (a task started or finished)
and `log` (a line of a task's output). A run that
produces more than 5000 events is cut off with one `truncated` event, the state
changes are always kept.

### Repositories

A run from a `ref` names a repository and a ref in its request. The repository is written
`host/path`, such as `github.com/corp/payments` or `gitlab.corp.com/platform/team/tool`;
the server builds the address from it (`https://host/path.git`), a url, a port or
credentials in the request are refused with `400`. Two lists decide whether it may be
used, and a run needs both:

1. **The caller's `repos`**, the patterns of their entitlements added up
   ([Entitlements](#entitlements)). A repository outside of them is `403 you may not run
   from <repo>` at submit, before anything is approved or queued. A caller without `repos`
   can not start runs from a ref.
2. **The server's `sources`**, the repositories it can read at all. `match` is a pattern
   (`github.com/corp/payments` exactly, `github.com/corp/*` for one level,
   `gitlab.corp.com/platform/**` for a group with its subgroups, which covers GitLab
   subgroups) and the first source that matches decides. A repository none covers is
   `400 this server can not read <repo>`.

Both lists use the same patterns, host names and paths are compared in lower case.

**The credential** is a secret of a secret provider, read as a service account of the
operator, like the secrets of a task: `secret.from` is `provider:reference`, `account` is
the account it is read as, and `username` (default `x-access-token`) is the user name of
the basic authentication the token is sent with. A provider command can mint a
short-lived token, for example of a GitHub App; it is read again after a minute. A source
without a `secret` is read anonymously. The token goes to git for that one fetch through
the environment of the git process, scoped to the host of the repository, so it is never
an argument, never written to `.git/config` or the checkout, never in the environment of a
task, and masked in the logs of the run. The account that reads repositories is the
server's own: no entitlement may name it and no build file may use it for a secret.

**Pinning.** The server resolves the ref when the run is submitted, with `git ls-remote`:
`refs/heads/<ref>`, else `refs/tags/<ref>` (an annotated tag to its commit). A name that is
both a branch and a tag, or neither, is `400`, a repository it can not reach is `502`. The
run stores the repository, the ref and the `commit`, and the approver sees them. The
executor fetches the ref and fails the run if it no longer points to that commit, so a
branch that moved after the approval does not run other code than the one approved. A
40-digit commit hash is taken as it is; an account with `refs` refuses one, because it
names no branch.

### Executing a run

The server runs the tasks of an accepted run on its own machine, with the same engine
as `hammerkit run`, so the `local` and `docker` runtimes and the task cache work as
they do there. Each run executes in a process of its own (`hammerkit server-run`, started
by the server):

1. It fetches the ref of the repository, as pinned to its commit when the run was
   submitted (see [Repositories](#repositories)), into a directory made for the run. A ref
   that is not a plain branch, tag or commit name is refused.
2. It writes the files of the published version over the checkout, so the tasks are
   the published ones whatever the build file in the repository says. A file that would
   land in `.git` (in any spelling a case-insensitive file system reads as that) or
   behind a symbolic link of the checkout is refused.
3. It starts the process of the run in the checkout and runs the tasks in the order they
   were named (or the ones the labels select), stopping at the first one that fails, and
   reports each task and its output as events. Cancelling the run stops the process with
   `SIGTERM`, so the engine stops its tasks and removes its containers, and kills it after
   15 seconds.
4. It removes the directory, whether the run succeeded, failed or was cancelled.

The process starts with an environment the server builds, not with its own: the variables
`runs.env.allow` lists, plus `runs.env.set`, and a `HOME` that is an empty directory of the
run's alone. So what the engine reads of its process (the docker host, registry logins in
the home directory, cloud credentials) is what the operator gave runs and nothing else; a
private registry needs `DOCKER_CONFIG` in the allowlist, pointing to a login the operator
chose for runs. Tasks do not get the environment of the process either, only their own
`envs` and the secrets they declare.

The task cache is kept below the server's `storage` directory, one cache for the runs of
a repository and one per caller for uploads. A run from an upload can therefore not leave
an entry that a run from a reviewed repository finds. A task is keyed by its definition
and its sources, not by where the checkout is.

A run fails with the reason when the server does not list the repository, when the ref
can not be fetched or has moved, when it comes from an `upload`: uploads are not
supported by the executor yet, use `source: ref`. Cancelling a run stops the fetch or
the running task.

Before it starts, the executor derives the accounts of the run again from the pinned
files with the run's environment, and fails the run if it would use one it was not
admitted for. The secrets of the tasks are read as the accounts of the server config, by
the provider commands, and a secret of any other account is refused when it is fetched.

**One server is one trust level.** The process of a run is not a sandbox. It runs as the user
of the server, a `local` task reads everything that user can read, and a container task can
use the docker daemon the server is configured for. Accounts keep credentials apart (a task
only reads the secrets of the accounts its run was admitted for), but they do not keep code
apart on one machine. Do not mix production and untrusted agents on one server: run
them on different servers, each with the accounts of its own level, and with `local` only on
a server whose users you trust with the machine. The storage directory and the other runs of
a server are inside what a `local` task can read.


### Limits and restarts

One caller can not take the machine. Per caller (issuer and subject) the server counts the runs that wait
for an approval (`runs.limits.waiting`) and the runs in the queue (`runs.limits.queued`); a submit over
either is answered `429` and says which. At most `runs.limits.running` runs of one caller execute at the
same time, and the next run in the queue whose caller has a place left starts first, so one caller with
many runs does not keep the others waiting. A run that executes longer than `runs.maxDuration` is stopped
and fails with that reason. The log of a run is cut off at `runs.maxLogBytes` with a `truncated` event;
the state changes are always kept.

Runs are written down when their state changes. On start the server takes them back:

* finished runs keep their state, events and logs;
* runs that wait for an approval wait on, for the time that was left, and are rejected when it has passed;
* runs that were queued or running when the server stopped have failed with it: `the server stopped while
  the run was running, submit it again`.

A graceful stop (SIGTERM) leaves the waiting runs waiting, and cancels the queued and running ones.

`kill -HUP <pid>` reads the config file again and takes over its `entitlements`: who may use which account,
which repositories and which build files changes for the next request, no restart and no run is touched.
Entitlements that name an account or issuer the running server does not have are refused and the old ones
stay. Everything else (accounts, issuers, providers, sources, limits) is read at start only, the server says
which keys of the file differ and need a restart. SIGHUP is not available on Windows.

## Approvals

Some work should not happen because one identity asked for it: a deploy with the
production key, a task with access to customer data. Access to a service account comes
at two levels for that, see [Entitlements](#entitlements). Whoever may **use** an
account runs on it directly. Whoever may only **request** it can ask for a run, which
waits in state `awaiting-approval` until somebody who may use that account approves it.
This suits an agent or a developer who proposes a deployment and a person who confirms
it.

```yaml
entitlements:
  - group: { iss: https://login.example.com, name: release-managers }
    accounts: { op-payments-prod: use }
  - group: { iss: https://login.example.com, name: eng-payments }
    accounts: { op-payments-dev: use, op-payments-prod: request }
    builds: run
approvals:
  timeout: 1h        # how long a run waits, default 1h
  maxWaiting: 100    # runs waiting at the same time, default 100
```

* The accounts of a run are derived from the secrets of the published, hash-pinned
  build file, see [Accounts](#accounts). Nothing in the request can change them, so
  every run that reads a production secret as a requester is held, whatever its tasks
  are called or labelled, and whoever may [publish](#build-files) cannot lift it.
* A run needs an approval for the accounts the caller can only request, the others
  they use. `deploy` waits for `op-payments-prod` while `test` in the same run does not.
* An approver covers every account they may `use`. A run that waits for accounts A and
  B is released as soon as the approvals cover both: one person who uses both is
  enough, otherwise two approve, one per account. Each account has its entry in the
  run's `approvals`, with who approved it. They share one expiry: a run that nobody
  covers within `timeout` is rejected, and so is one that any covering approver
  rejects. More than `maxWaiting` waiting runs are refused with `503`. A run that waits
  is cancelled when the server stops, like every other.
* A request for an account that nobody may use is refused at once (`409 nobody can
  approve <account>`) and not left to expire.
* A caller approves what they have access to, and nobody approves their own run. A
  caller who uses none of the accounts that wait sees nothing of the run. Approvers see
  the published build files, so they can read what they approve, and nothing more.
* The approver is shown what to decide on: the tasks and services the run executes
  with their dependencies as `plan` (commands, image, the secrets and the account each
  is read as, mounts, ports and the `flags` to look at first, never a value), the
  accounts, the version, the source and the options. Who uses an account a run needed
  approved may also read that run (`GET /v1/runs/<id>` and its events) and cancel it;
  `GET /v1/runs` stays the caller's own.
* What an approval cannot cover is what the code does: pinning commands does not pin the
  code they run, so an account that matters should also be limited to `source: [ref]`
  and `refs`.

| Call | What it does |
| --- | --- |
| `GET /v1/approvals` | The runs waiting for an approval the caller can give, with who asked, the build file version, tasks, accounts, source and options. |
| `GET /v1/approvals/<id>` | One of them. |
| `POST /v1/approvals/<id>/approve` | Approve the accounts the caller uses; the run is queued when all are covered (`already-approved` is `409`). The body is optional: `{ "reason": "..." }`. |
| `POST /v1/approvals/<id>/reject` | End the run; the reason (up to 500 characters) becomes its `error`. |

What a caller may not approve does not exist for them (`404`), and a run that is no
longer waiting is `409`. Each call is logged with who decided and the result, and the
decision is an event of the run, so the one who asked sees who approved it.
`hammerkit remote accounts` shows the caller's levels. The command line has [`remote approvals`, `approve` and `reject`](/docs/cli/remote#approving-runs).

## Discovery

`GET /.well-known/hammerkit` needs no token and returns what the server is, so a
client can check it before signing in:

```json
{
  "name": "hammerkit",
  "version": "1.17.0",
  "protocol": 1,
  "issuers": [
    {
      "issuer": "https://login.example.com",
      "audience": "hammerkit",
      "clientId": "hammerkit-cli",
      "scope": "openid api://hammerkit/.default"
    }
  ],
  "backend": { "type": "host", "platform": { "os": "macos", "arch": "arm64" } }
}
```

`GET /healthz` answers `{"status":"ok"}` for a load balancer or a process manager.
Every other path needs a token.
