---
title: "Extending"
description: "A task can be used as a base template and extended. This is intended to reduce duplicate task definitions."
---
Extending tasks avoids a lot of duplicated task definitions in bigger projects and monorepos. With the `extend` property, a task uses another task's configuration as a template.

The following sections and examples use the two tasks in a `build.tsc.yaml` file, shown below. The [catalog](/docs/catalog/tsc) has a maintained `tsc` entry that you can include instead of copying.

```yaml title="build.tsc.yaml"
tasks:
  install:
    src:
      - package.json
      - package-lock.json
    generates:
      - node_modules
    cmds:
      - npm ci
      
  build:
    deps: [ install ]
    src:
      - tsconfig.json
      - src
    cmds:
      - node_modules/.bin/tsc
    generates:
      - dist
```

### Extend a task

Extending `tsc:build` uses all of its properties as a base. If nothing else is defined, the result is an exact copy that runs in the working directory of the current build file.

```yaml title=".hammerkit.yaml"
tasks:
  build:
    extend: tsc:build
    
includes:
  tsc: ./build.tsc.yaml
```

### Override properties in an extend

An extending task can override any property, whether the base defines it or not. Single
values such as `image`, `shell`, `cache` and `timeout` are replaced by the extending
task's own value. Lists and maps are **added to** the base's instead:

| Property | With `extend` |
|---|---|
| `image`, `shell`, `cache`, `timeout`, `network`, `args`, `runner` | The task's own value replaces the base's. |
| `cmds`, `src`, `generates`, `mounts` | The base's entries come first, the task's own follow. |
| `deps`, `needs` | Both are used. |
| `envs`, `labels` | Merged. The task's own value wins for a name both define. |
| `build` | Merged key by key. A key the task sets replaces the base's, see [image builds](#image-builds). |

The `envs` of the base also include the top-level `envs` of the build file it comes from,
so a base that reads `$NODE_VERSION` keeps its default when you extend it.

```yaml title=".hammerkit.yaml"
tasks:
  build:
    extend: tsc:build
    src:
      - ../../tsconfig.base.json
    
includes:
  tsc: ./build.tsc.yaml
```

Here `build` runs the base's commands against the base's sources plus
`../../tsconfig.base.json`.

### Container properties without an image

A task that extends a container task takes the base's image, so it may set `mounts`,
`volumeSize` and `capAdd` without an `image` of its own:

```yaml title=".hammerkit.yaml"
tasks:
  build:
    extend: base:node
    mounts:
      - .git
    cmds:
      - git log

includes:
  base: ./build.base.yaml
```

When neither the task nor its base has an image, they are an error:
`task build sets mounts, but neither it nor its base has an image`.

A base's `volumeSize`, `capAdd`, `resources` and `secrets` are not passed on; set them on
the extending task when it needs them.

### Image builds

A task with [`build`](/docs/task/image-builds) extends like any other. `build` is merged key by
key: a key the task sets replaces the base's, a list such as `tags` or `login` included, and the
keys it leaves out come from the base.

```yaml title=".hammerkit.yaml"
tasks:
  image-api:
    timeout: 30m
    build:
      dockerfile: api/Dockerfile
      tags: ghcr.io/acme/api:main
      push: true
      login:
        - registry: ghcr.io
          user: acme-ci
          password:
            from: env:GITHUB_TOKEN

  image-worker:
    extend: image-api
    build:
      dockerfile: worker/Dockerfile
      tags: ghcr.io/acme/worker:main
```

`image-worker` builds `worker/Dockerfile`, pushes it as `ghcr.io/acme/worker:main` with the
login of `image-api` and stops after 30 minutes. A task without a `build` of its own takes the
base's whole.

hammerkit writes the image and the command of a task that builds one, so neither the task nor
its base may have `image`, `cmds`, `shell`, `args`, `mounts` or `capAdd`:
`task image-worker has build and cmds, from it or the task it extends`. So a task with `build`
can't extend a container task, and a container task can't extend one with `build`.

### Reset inherited values

To take nothing from the base for a property, name it in `reset`. The task's own value for
that property still applies. In this example the dependencies are cleared, so the task runs
without depending on `install`:

```yaml title=".hammerkit.yaml"
tasks:
  build:
    extend: tsc:build
    reset: [deps]
    
includes:
  tsc: ./build.tsc.yaml
```

`reset` accepts `deps`, `needs`, `src`, `generates`, `cmds`, `mounts`, `envs`, `labels` and
`build`.
It is an error without `extend`. An empty `deps: []` does not clear the base's
dependencies, because the lists are added together.

### Naming the base task

`extend` uses the same `<prefix>:<task>` addressing as [dependencies](/docs/task/dependencies):
the part before the colon is the [include](/docs/build-file/includes) (or
[reference](/docs/build-file/references)) prefix, and the part after it is the task
name in that file. `extend: tsc:build` means "the `build` task from the file
included as `tsc`". To extend a task in the *same* file, use its bare name
(`extend: build-base`).
